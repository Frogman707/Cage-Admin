# 튜토리얼 — 로그인부터 첫 승인까지

> **분류**: Tutorial (학습 지향) · **소요**: 약 15분
> **관련 문서**: [화면 58개](reference-screens.md) · [앱 레퍼런스](reference-partner-admin-app.md)

파트너 어드민을 처음 켜고, 데모 데이터를 만들고, 회원에게 돈을 지급하고, 그 돈이 Firestore
원장에 어떻게 남는지까지 직접 확인합니다. 3단계 안에 대시보드에 숫자가 채워집니다.

끝나면 이 세 가지를 알게 됩니다.

- 58개 화면이 어떻게 배치돼 있는지
- 승인 버튼 하나가 Firestore에 몇 개의 문서를 쓰는지
- 회원 보유금이 어디에도 저장돼 있지 않고 매번 계산된다는 것

---

## 시작 전에

> **경고 — 실제 Firestore에 씁니다.**
> [`shared/cage-ui.js:8`](../../shared/cage-ui.js#L8)의 Firebase 설정은 실제 프로젝트
> `cage-admin-25bbf`를 가리킵니다. Hosting 에뮬레이터를 써도 데이터는 에뮬레이터가 아니라
> **운영 Firestore**로 갑니다. "데모 데이터 생성"과 "데이터 초기화"도 마찬가지입니다.
> 공유 프로젝트라면 다른 사람 작업을 지울 수 있으니, 초기화 버튼은 누르지 마세요.

**필요한 것**

- Firebase CLI 로그인, 프로젝트 `cage-admin-25bbf` 접근 권한
- 최신 브라우저 (Chrome / Edge / Firefox)
- 저장소 클론

빌드 단계는 없습니다. `npm install`도 필요 없습니다 — 앱은 정적 파일이고 Firebase SDK는
CDN에서 옵니다.

---

## 1단계: 사이트 띄우기

저장소 루트에서:

```bash
firebase use cage-admin-25bbf
firebase emulators:start --only hosting
```

출력에 Hosting URL이 나옵니다. 기본값은 `http://localhost:5000`입니다.

브라우저에서 **`http://localhost:5000/partner-admin/`** 을 엽니다. 로그인 화면이 보이면 정적
파일 제공이 정상입니다.

```
┌─────────────────────────┐
│     PARTNER ADMIN       │
│          v5.0           │
│                         │
│  파트너 ID   [ admin  ]  │
│  비밀번호    [ ••••   ]  │
│       [ 로그인 ]         │
│                         │
│  데모 계정: admin / 0000 │
└─────────────────────────┘
```

---

## 2단계: 로그인

화면에 적힌 대로 입력합니다.

```text
파트너 ID: admin
비밀번호: 0000
```

로그인하면 좌측에 12개 그룹의 내비게이션, 상단에 시계와 로그인한 직원 이름(`Eric`)이
나타납니다.

**방금 무슨 일이 있었나.** 페이지가 로드될 때
[`ensureDefaultStaff()`](../../partner-admin/app.js#L168)가 `partnerStaff` 컬렉션을 확인해,
비어 있으면 `admin` / `0000` 문서를 만들었습니다. 로그인은 그 문서를 읽어 비밀번호를 문자열로
비교했을 뿐입니다. Firebase Authentication 세션은 만들어지지 않습니다.

> **참고**: ID와 비밀번호를 둘 다 비운 채 로그인해도 통과합니다 —
> [P-02](explanation-known-gaps.md#p-02--빈-입력으로-로그인하면-admin이-된다).

대시보드가 전부 `0`이면 정상입니다. 아직 데이터가 없습니다.

---

## 3단계: 데모 데이터 만들기 — 첫 결과

좌측 내비게이션 **맨 아래**에 두 개의 작은 버튼이 있습니다.

```
Partner Cage Ops
CAGE ADMIN 5.0
 ┌───────────────────┐
 │  데모 데이터 생성   │   ← 이걸 누릅니다
 ├───────────────────┤
 │  데이터 초기화      │   ← 누르지 마세요
 └───────────────────┘
```

**데모 데이터 생성**을 누르면 확인 모달이 뜹니다. "확인"을 누르세요.

"데모 데이터 생성 중..." 토스트가 뜨고, 완료되면
`데모 데이터 생성 완료 (회원 40명, 라운드 150개)` 가 표시됩니다.

**대시보드가 채워집니다.**

| 카드 | 대략적인 값 |
| --- | --- |
| 총회원 | 40 |
| 총 보유금 | 수천만 PHP (무작위) |
| 총 포인트 | 수만 |
| 총 쿱프 | **0** ← 항상 0입니다 ([P-07](explanation-known-gaps.md#p-07--총-쿱프가-항상-0이다)) |

차트 4개도 그려집니다. 회원가입현황 2개(최근 16일), 유저활동 2개(날짜별·시간별).

> **오류가 났다면.** 콘솔에
> `A write batch can no longer be used after commit() has been called.` 가 보이면
> [P-09](explanation-known-gaps.md#p-09--시드의-flush가-await되지-않는다)입니다. 시드가 400건
> 경계에서 실패하는 알려진 결함입니다. 회원관리 > 유저리스트에서 실제 생성된 회원 수를
> 확인하세요.

여기까지 3단계입니다. 이제 실제 운영 동작을 봅니다.

## 4단계: 디파짓 승인하기

좌측 **회원관리 > 디파짓관리**를 엽니다.

`대기` 상태 요청이 3건 있습니다. 아무 행의 **승인** 버튼을 누르세요. 회원 ID와 금액을
메모해 둡니다 (예: `SEH1023`, `250,000`).

승인하면 "승인되었습니다" 토스트가 뜨고 상태가 `승인`으로 바뀝니다.

**Firestore에 무슨 일이 있었나.** [`approveDeposit(id)`](../../partner-admin/app.js#L890)가
두 단계를 실행했습니다.

```
1) 트랜잭션 — depositRequests/{id}
     status: '대기'인지 확인 → '승인'으로 변경
     (이미 처리됐으면 여기서 중단. 중복 입금 방지)

2) writeMemberLedgerEntry() — batch 하나에 두 문서
     memberLedger/{새UUID}          amount: +250000, category: 'deposit'
     balanceTotals/member_SEH1023   balance: increment(+250000)
```

같은 트랜잭션 가드가 결제처리 승인에도 걸려 있습니다. 두 직원이 동시에 눌러도 한 번만
입금됩니다.

**승인 버튼을 다시 누를 수 있나요.** 없습니다. 상태가 `승인`이 되면 액션 열이 `—`로 바뀝니다.
혹시 다른 탭에서 이미 승인된 요청을 눌러도 "이미 처리된 요청입니다"가 뜹니다.

## 5단계: 보유금이 어떻게 계산되는지 보기

좌측 **계정관리**를 엽니다. 4단계에서 메모한 회원 ID를 검색창에 입력하세요.

보유금액 열의 숫자가 방금 승인한 250,000을 포함합니다.

이 숫자는 `members` 문서에 저장돼 있지 않습니다.
[`getBalances()`](../../partner-admin/app.js#L249)가 `memberLedger` **전체**를 읽어 회원별로
합산해 만듭니다.

```
memberLedger에서 memberId === 'SEH1023'인 모든 행
  {amount: +300000, category:'deposit'}     ← 시드가 만든 것
  {amount:  -50000, category:'bet'}
  {amount:  +97500, category:'payout'}
  {amount: +250000, category:'deposit'}     ← 방금 4단계에서 승인한 것
                    ─────────
       balance =     597500
```

**직접 확인하려면** 회원관리 > 유저리스트에서 그 회원의 행을 클릭하세요. 회원 상세 모달이
열립니다. **입출금** 탭에 방금 승인한 항목이 "디파짓 승인" 메모와 함께 맨 위에 있습니다.

**어카운트정보** 탭에는 같은 원장을 카테고리별로 나눈 합계가 있습니다.

| 항목 | 원장 카테고리 |
| --- | --- |
| 보유금 | 포인트를 뺀 전체 합 |
| 누적입금 / 누적출금 | `deposit` / `withdraw` |
| 누적베팅 / 누적페이아웃 | `bet` / `payout` |

## 6단계: 직접 보유금 지급하기

계정관리 화면으로 돌아가, 같은 회원 행의 **+ 추가** 버튼을 누릅니다.

```
금액: 100000
메모: 튜토리얼 테스트 지급
```

**처리**를 누르면 "처리되었습니다" 토스트가 뜨고 화면이 다시 그려집니다. 보유금액이
100,000 늘어났습니다.

[`submitBalanceAdjust()`](../../partner-admin/app.js#L411)가 쓴 것:

| 컬렉션 | 내용 |
| --- | --- |
| `memberLedger` | `{amount:+100000, category:'deposit', memo:'튜토리얼 테스트 지급', staff:'admin', deviceId:...}` |
| `balanceTotals` | `member_{회원ID}`의 `balance`를 `+100000` 증분 |
| `memberActionLogs` | `{action:'지급 100,000', staff:'admin'}` |

**차감도 같은 모달입니다.** `− 차감`은 `mode:'withdraw'`로 열려 금액에 음수 부호를 붙이고
카테고리를 `withdraw`로 바꿉니다.

> **잔액 검사가 없습니다.** 보유금이 0인 회원에게 1억을 차감해도 그대로 실행됩니다.
> 결과는 마이너스 잔액입니다.

---

## 7단계: 감사 로그 확인

**관리자 관리 > 회원액션로그**를 엽니다.

6단계의 지급이 맨 위에 있습니다.

```
2026-08-14 15:32 | SEH1023 | 지급 100,000 | admin
```

**관리자 관리 > 관리자로그**도 열어 보세요. 여기에는 6단계 지급이 **없습니다.**

두 로그의 쓰임이 다릅니다.

| 로그 | 기록하는 것 | 쓰는 화면 |
| --- | --- | --- |
| `memberActionLogs` | 특정 회원에게 한 일 | 계정관리, 소속이동 |
| `adminLogs` | 회원과 무관한 운영 조작 | 아바타 승인, 라운드 수정/취소 |

디파짓 승인(4단계)은 **어느 쪽에도 남지 않습니다.** 원장의 `staff` 필드에만 처리자가
기록됩니다.

## 8단계: Firestore에서 직접 대조하기

[Firebase 콘솔](https://console.firebase.google.com/project/cage-admin-25bbf/firestore)에서
`memberLedger` 컬렉션을 열고, 필터를 겁니다.

```
memberId == SEH1023   (4단계에서 메모한 ID)
```

방금 만든 문서 두 개가 보입니다.

```js
// 4단계 — 디파짓 승인
{
  memberId: 'SEH1023',
  amount: 250000,
  category: 'deposit',
  memo: '디파짓 승인',
  staff: 'admin',
  createdAt: <서버 타임스탬프>,
  clientCreatedAt: '2026-08-14T15:28:11.402Z',
  deviceId: '4f9c...'
}

// 6단계 — 직접 지급
{
  memberId: 'SEH1023',
  amount: 100000,
  category: 'deposit',
  memo: '튜토리얼 테스트 지급',
  staff: 'admin',
  ...
}
```

`createdAt`은 서버 타임스탬프, `clientCreatedAt`은 브라우저 시각입니다. 둘을 같이 남기는
이유는 클라이언트 시계가 틀렸을 때 나중에 판별하기 위해서입니다. `deviceId`도 같은 목적으로,
`localStorage`에 저장된 브라우저별 고유값입니다 — 보안 경계가 아니라 조사용 단서입니다.

이제 `balanceTotals` 컬렉션에서 `member_SEH1023` 문서를 엽니다.

```js
{ balance: 350000 }   // 4단계 250,000 + 6단계 100,000
```

**원장 합계와 다릅니다.** 시드가 만든 원장은 `balanceTotals`에 반영되지 않기 때문입니다
([P-08](explanation-known-gaps.md#p-08--데모-시드가-balancetotals를-갱신하지-않는다)).
`balanceTotals`는 아직 어떤 화면도 읽지 않는 이중 쓰기 단계이므로 화면에는 영향이 없습니다
([보유금 아키텍처 설계](../BALANCE_ARCHITECTURE_DESIGN.md)).

## 만든 것

파트너 어드민을 처음부터 끝까지 한 바퀴 돌았습니다.

- **58개 화면**이 12개 그룹으로 묶여 있고, 약 40개는 설정 객체 하나로 만들어진 리스트 화면입니다

- **감사 로그가 두 갈래**로 나뉘고, 디파짓 승인은 어느 쪽에도 안 남습니다

## 문제 해결

### 로그인 후 화면이 스피너에서 멈춥니다

Firestore 접근이 실패했습니다. 브라우저 콘솔을 확인하세요.

- `permission-denied` — [`firestore.rules`](../../firestore.rules)가 배포되지 않았거나
  `staff` 컬렉션을 읽으려 했습니다. `firebase deploy --only firestore:rules`로 배포합니다.
- 네트워크 오류 — `firebase use`가 올바른 프로젝트를 가리키는지 확인합니다.

리스트 화면은 오류가 나도 스피너에 멈추지 않도록
[에러 콜백](../../partner-admin/app.js#L294)이 걸려 있습니다. 스피너가 멈춘다면 전용 렌더러
화면(대시보드·통계 등)입니다.

### 데모 데이터 생성이 끝나지 않습니다

[P-09](explanation-known-gaps.md#p-09--시드의-flush가-await되지-않는다)입니다. 콘솔의 오류를
확인하고, 부분 생성된 데이터로 진행하거나 초기화 후 재시도합니다.

### 대시보드 숫자가 갱신되지 않습니다

대시보드는 전용 렌더러라 실시간 구독이 없습니다. 좌측에서 다른 화면으로 갔다가 돌아오거나,
리스트 화면의 "새로고침" 버튼을 누릅니다. 리스트 화면(약 40개)은 `onSnapshot` 구독이라
자동으로 갱신됩니다 — 단, 표 위의 요약 카드는 마운트 시점 값으로 고정입니다.

### 회원 보유금이 마이너스입니다

정상 동작입니다. 차감·베팅에 잔액 검사가 없습니다. 계정관리에서 `+ 추가`로 되돌릴 수
있습니다.
