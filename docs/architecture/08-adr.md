# 08. 설계 결정 기록 (ADR)

각 결정에 대해 **대안과 트레이드오프**를 남긴다. 나중에 뒤집을 때 무엇을 재검토해야 하는지 알기 위해서다.

## ADR-001 · Firestore를 폐기하고 PostgreSQL로 이전한다

**상태:** 채택

### 맥락

Firestore가 유일한 데이터베이스이며 브라우저가 직접 접근한다. 목표는 큰 금액을 다루는 실서비스다.

### 결정

Firestore를 완전히 폐기한다. 읽기 모델로도 남기지 않는다.

### 근거 — 애플리케이션 수정으로 해결 불가능한 엔진 제약

| # | 제약 | 이 도메인에서 터지는 지점 |
|---|---|---|
| 1 | 쿼리 결과에 트랜잭션 불가 | "잔액 = 원장 합산"을 읽으면서 원자적으로 쓸 수 없다. 오버드래프트 차단 불가 |
| 2 | 다중 문서 불변식 강제 없음 | 분개 합 = 0을 DB가 지킬 수 없다 |
| 3 | 스키마 강제 없음 | `inn`/`out` vs `amt` 드리프트가 **예외 없이 0 반환** |
| 4 | 조인 없음 | 계층 커미션·정산·대사가 전부 앱 메모리로 |
| 5 | 숫자 = IEEE 754 | 금액 표현에 부적합 |
| 6 | 집계 비용이 문서 수에 비례 | append-only 원장은 영원히 커진다 |
| 7 | 쓰기 권한 제어가 규칙 DSL 한 겹 | 역할 분리·저장 프로시저 강제·권한 회수 없음 |

1~2가 결정적이다. **자금 불변식을 강제할 수단이 엔진에 없다.**

### 대안

- **Firestore 유지 + Cloud Functions 게이트** — 1·2가 해결되지 않는다. 잔액 스냅샷 문서로 우회할 수 있으나 이중 기록이 되고 스냅샷과 원장의 정합성을 다시 검증해야 한다
- **Firestore를 읽기 모델로 유지 (CQRS)** — 쓰기 경로가 두 배가 되고 진실 공급원이 둘이 된다. 실시간은 WebSocket으로 대체 가능하므로 이득이 없다

### 결과

- 실시간 구독을 WebSocket으로 재구현해야 한다 ([02](02-target-architecture.md) 4절)
- Firestore 특유 대응 코드가 소멸한다 (long polling · 오프라인 캐시 · 재구독 백오프)
- 프런트엔드 재작성이 필요하다

## ADR-002 · 서비스를 5개로 분해한다 (12개가 아니라)

**상태:** 채택

### 결정

Ledger & Cage Core · Player & Game · Identity · Notification · Gateway(API + Realtime).

### 근거

**서비스 경계는 자금 불변식 경계와 일치해야 한다.** Ledger와 Cage를 나누면 케이지 바이인이 두 서비스에 걸쳐 Saga가 필요해진다. 통합하면 한 트랜잭션 안의 분개 2줄이다.

Player & Game만 분리하는 이유는 **부하가 아니라 런타임 형태**다. 테이블당 상주 single-writer 워커가 필요하며, 요청/응답 서비스와 배포·확장 축이 다르다.

### 분리 재검토 기준

다음 중 하나라도 해당하면 그때 쪼갠다.

- 특정 도메인의 배포 주기가 나머지와 크게 어긋난다
- 특정 도메인의 확장 축이 다르다 (CPU vs 커넥션 vs 스토리지)
- 팀이 분리되어 코드 소유권 경계가 필요하다
- 장애 격리가 필요하다 (한 도메인의 장애가 전체를 멈춘다)

**"마이크로서비스가 모범 사례라서"는 기준이 아니다.**

## ADR-003 · 금액은 `BIGINT` 최소 단위 정수

**상태:** 채택

### 결정

모든 금액 컬럼은 `BIGINT`, 통화 최소 단위(PHP = 센타보). 컬럼명에 `_minor` 접미사를 붙인다.

### 근거

PostgreSQL 위키 "Don't Do This"는 `money` 타입을 쓰지 말고 `numeric` 또는 정수를 쓰라고 명시한다. 남은 두 후보 중:

| | `NUMERIC` | `BIGINT` 최소 단위 |
|---|---|---|
| 정확성 | 정확 | 정확 |
| 속도 | 정수 대비 매우 느림 | 빠름 |
| 저장 | 가변 | 8바이트 고정 |
| 반올림 모호성 | 소수 자릿수 혼용 가능 | 구조적으로 불가 |

원장은 덧셈이 지배적이고 행 수가 계속 늘어난다. 정수 우위가 크다.

`NUMERIC`은 **환율·요율 계산에만** 쓴다 (곱셈·나눗셈이 있는 곳).

### 결과

- 애플리케이션이 통화별 `scale`을 알아야 한다 → `ledger.currencies` 테이블
- API 필드명에 `_minor`를 강제해 단위 혼동을 차단한다
- 현행 `Math.abs(x − y) > 0.001` 허용 오차가 불필요해진다

### 범위 확인

```
9,223,372,036,854,775,807 센타보 ≈ 92,233조 페소
```
단일 계정·단일 거래 모두 충분하다.

## ADR-004 · Read Committed + 명시적 행 잠금 (Serializable 아님)

**상태:** 채택

### 결정

자금 트랜잭션은 기본 격리 수준(Read Committed)에서 실행하고, 잔액 행을 `SELECT ... FOR UPDATE`로 잠근다. 잠금 순서는 `account_id` 오름차순으로 고정한다.

### 근거

`SERIALIZABLE`은 직렬화 이상을 전부 막지만 문서가 재시도를 필수로 요구한다.

> "Applications using this level must be prepared to retry transactions due to serialization failures."
> "It is important that an environment which uses this technique have a generalized way of handling serialization failures (which always return with an SQLSTATE value of '40001')"

이 시스템이 필요로 하는 직렬화는 **같은 계정에 대한 동시 접근**뿐이다. 행 잠금으로 정확히 그 지점만 직렬화하면 40001 재시도 부담 없이 불변식을 지킬 수 있고 처리량도 낫다.

데드락 회피는 문서가 명시한 표준 대응을 따른다.

> "The best defense against deadlocks is generally to avoid them by being certain that all applications using a database acquire locks on multiple objects in a consistent order."

**잠금 순서는 `post_transaction()` 함수 안에 강제되어 호출자가 위반할 수 없다.**

### 재검토 기준

읽기-검사-쓰기가 잔액 외의 조건(예: 복수 계정에 걸친 복합 조건)에 의존하기 시작하면 `REPEATABLE READ` 또는 `SERIALIZABLE` + 재시도 루프를 재검토한다.

## ADR-005 · 불변식을 지연 제약 트리거로 강제한다

**상태:** 채택

### 결정

- 분개 균형(합 = 0) → `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED`
- 잔액 하한 → `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED`

### 근거

**분개 균형:** 분개는 여러 행에 나뉘어 삽입된다. 첫 행 시점에는 합이 0이 아니다. 커밋 시점 검사가 필수다.

**잔액 하한:** `CHECK` 제약을 쓰고 싶지만 **PostgreSQL에서 `CHECK`는 `DEFERRABLE`이 될 수 없다.** `DEFERRABLE`을 받는 것은 `UNIQUE` · `PRIMARY KEY` · `EXCLUDE` · `REFERENCES`뿐이다.

`CHECK`를 즉시 평가로 걸면 **분개 삽입 순서에 의존하는 스키마**가 된다. 게임 종료 정산은 최대 7개 계정에 걸치므로 순서 의존은 실질적 위험이다.

지연 제약 트리거는 문서가 정의한 용도에 정확히 부합한다.

> "Constraint triggers are expected to raise an exception when the constraints they implement are violated."

### 제약 (문서 명시)

- `AFTER`만 가능
- `FOR EACH ROW`만 가능
- 일반 테이블에만 생성 가능

### 트레이드오프

행마다 트리거가 실행된다. 거래당 분개가 2~7개이므로 부담은 작다. 대량 적재(마이그레이션)에서는 `SET CONSTRAINTS ALL DEFERRED`로 묶고 마지막에 한 번 검증하는 방식을 쓴다.

## ADR-006 · 해시 체인은 지점별. 고빈도 거래는 제외

**상태:** 채택

### 결정

`ledger.transactions`에 `prev_hash` / `hash` 체인을 둔다. 범위는 **지점별**. 플레이어 베팅은 체인에서 제외하고 일 단위 머클 앵커링으로 대체한다.

### 근거

전역 단일 체인은 모든 거래를 직렬화한다. 체인 헤드 행이 전 시스템의 병목이 된다.

지점별 체인은:
- 지점 내 순서만 보장한다 (감사에 충분)
- 지점 수만큼 병렬성을 확보한다
- 케이지 거래량(시간당 수십 건)에 여유가 있다

베팅은 초당 수십~수백 건이 가능하므로 지점 체인에 넣으면 케이지 거래까지 막힌다.

### 앵커링

일 단위로 각 지점 체인 헤드를 외부 저장소에 서명·보관한다. DB 전체가 침해되어도 과거 변조를 탐지할 수 있다.

### 트레이드오프

지점 간 거래 순서는 체인으로 증명되지 않는다. `recorded_at`(서버 시각)이 그 역할을 하며, 지점 간 순서가 회계적으로 중요한 사건은 지점 간 이체뿐인데 이는 단일 거래로 원자적이다.

## ADR-007 · Outbox는 폴링으로 시작한다

**상태:** 채택 (1차)

### 결정

Outbox relay를 `FOR UPDATE SKIP LOCKED` 폴링으로 구현한다. 논리 복제는 필요해지면 전환한다.

### 근거

| | 폴링 | 논리 복제 |
|---|---|---|
| 의존성 | 없음 | 복제 슬롯 관리 · 슬롯 미소비 시 WAL 누적 위험 |
| 지연 | 폴링 주기 (100ms 수준) | 수 ms |
| 운영 복잡도 | 낮음 | 슬롯 모니터링 필요 |
| 부하 | 주기적 쿼리 | 없음 |

케이지 운영에서 100ms 지연은 체감되지 않는다. 운영 단순성이 우선이다.

### 전달 보장

**at-least-once다.** relay가 발행 후 확인 전에 죽으면 중복 발행된다. 따라서 **구독자는 반드시 멱등해야 한다.** 이벤트에 단조 증가 `seq`를 실어 클라이언트가 중복을 무시한다.

### 전환 기준

- 폴링 쿼리가 DB 부하에 유의미하게 기여
- 지연 요구가 10ms 수준으로 강화

## ADR-008 · 9개 교대 카운터를 원장·재고 원장으로 승격한다

**상태:** 채택

### 맥락

현행 `SHIFT_FIELDS` 9개(`index.html:4935`)는 서로 독립적으로 누적되며 **상호 정합성을 검증할 수단이 없다.** 하나가 어긋나도 조용히 어긋난다.

### 결정

자금 성격 카운터는 원장 계정으로, 물리 칩 재고는 별도 재고 원장으로 승격한다. 9개 카운터는 파생값이 된다.

매핑표: [03-ledger-model.md](03-ledger-model.md) 4-3절.

### 근거

원장 계정으로 만들면 회계 항등식이 정합성을 자동 검증한다. 밸런싱 실사가 "카운터 9개를 눈으로 대조"에서 "계정 잔액 vs 실물 카운트 비교"가 된다.

### 결과

- **화면과 API 응답 형태는 유지한다** (`GET /branches/{b}/shift-counters`가 같은 9개 필드를 반환)
- 프런트엔드 변경이 거의 없다
- 마이그레이션 시 카운터 값을 옮기지 않는다. 개시 잔액에서 다시 파생된다

### 트레이드오프

파생 쿼리가 집계이므로 인덱스 설계가 중요하다. 필요하면 기간별 요약 테이블을 둔다.

## ADR-009 · 정정은 역분개. 삭제하지 않는다

**상태:** 채택

### 맥락

현행 게임 취소는 게임 문서와 롤링 이벤트를 **삭제**한다 (`deleteGameDoc`, `index.html:4613`). 메인케이지 항목도 삭제 가능하다 (`deleteMainCageEntry`, `:4750`).

### 결정

원장은 `UPDATE`/`DELETE`를 금지한다. 정정은 부호를 반전한 새 거래를 만들고 `reverses_tx_id`로 연결한다.

### 근거

삭제는 감사 추적을 파괴한다. 분쟁 시 "그런 거래가 있었는가"를 증명할 수 없다.

### 결과

- 취소된 게임의 이력이 남는다
- 화면은 `status = 'cancelled'`와 역분개 쌍을 표시해야 한다
- 데이터가 줄지 않는다 (보존 정책 필요)

## ADR-010 · 자체 인증. 외부 ID 공급자에 의존하지 않는다

**상태:** 채택

### 결정

Identity 서비스가 직원·회원 인증을 직접 소유한다.

### 근거

자금 시스템은 **즉시 무효화**가 가능해야 한다. 직원 해고·단말 분실 시 다음 토큰 만료를 기다릴 수 없다.

또한 이 도메인은 다음이 필요하다:
- 조작별 재인증(step-up) — 현행 `requestPinAuth`/`requestWithdrawAuth` UX 유지
- 출금 비밀번호라는 로그인과 분리된 별도 시크릿
- 4-eyes 승인과 연동된 역할 모델
- 인증 방식을 거래에 기록 (`transactions.auth_method`)

외부 공급자로 이 조합을 구성하면 결국 대부분을 자체 구현하게 된다.

### 트레이드오프

비밀번호를 직접 보관한다 → Argon2id + 페퍼 + 시도 제한이 필수다 ([06](06-security.md) 3절).

향후 SSO가 필요해지면 PostgreSQL 18의 OAuth 2.0 지원과 함께 재검토한다.

## ADR-011 · 케이지 계좌와 회원 보유금을 한 원장에 둔다

**상태:** 채택

### 맥락

현행은 `accounts`/`ledger`(케이지)와 `members`/`memberLedger`(플레이어)가 완전히 분리되어 있고, 두 원장 간 자금 이동이 불가능하다.

### 결정

계정 종류(`member_deposit` vs `player_wallet`)로만 구분하고 같은 `entries` 테이블을 쓴다.

### 근거

- 두 원장 간 이체가 **한 트랜잭션**이 된다
- 전역 항등식 하나로 전체 자금을 검증할 수 있다
- 회원이 케이지 손님이기도 한 경우가 자연스럽게 표현된다

### 트레이드오프

`entries` 테이블에 베팅 트래픽이 들어온다. 베팅량이 커지면 파티셔닝(`business_date` 범위 또는 `category` 기준)을 검토한다. 이는 스키마 변경 없이 가능하다.

### 필요한 정책

어느 방향으로 얼마까지 이체를 허용할지는 사업 결정이다. 기술적으로는 계정 종류 쌍 화이트리스트로 제한한다.

## ADR-012 · 회계 기간 엔티티가 `*Baseline` 스칼라를 대체한다

**상태:** 채택

### 맥락

현행 `cageConfig`는 정산 시점 누계를 스칼라 6개(`settleGameOutBaseline` 등, `index.html:4709`)로 박아 두고 이후 값에서 뺀다. 월정산은 메인케이지 누계·교대 카운터·게임 롤링을 **실제로 리셋**한다 (`:8274-8280`).

### 결정

`ledger.accounting_periods` 테이블을 두고 `open` → `frozen` → `settled` 상태를 관리한다. 동결된 기간에 속하는 거래 삽입은 트리거가 거부한다.

### 근거

- 리셋이 **데이터 파괴**에서 **기간 전환**으로 바뀐다
- 과거 기간 조회가 가능해진다 (현행은 리셋되면 사라진다)
- 동결 후 발견된 오류를 다음 기간 `adjustment`로 흡수하는 정식 경로가 생긴다

### 결과

- 월정산 화면의 "리셋" 동작이 "기간 마감"으로 바뀐다. **사용자에게 보이는 변화가 있다**
- 마감된 기간에 소급 입력하려는 시도가 오류가 된다. 운영 절차 안내 필요

## ADR-013 · 원장 코어와 연산 함수를 두 계층으로 분리한다

### 맥락

초안은 `ledger.post_transaction(entries JSONB)` 하나를 애플리케이션에 노출했다. 이 함수는 분개 합이 0인지, 잔액 하한을 넘지 않는지만 본다.

**그것만으로는 도둑질을 막지 못한다.** `member_deposit`을 대변 −X, `suspense`를 차변 +X로 기록하면 합은 0이고 `suspense`는 `allow_negative`라 하한 검사도 통과한다. 회계 항등식은 지켜진 채 돈이 창조된다.

### 결정

두 계층으로 나눈다.

| 계층 | 파일 | 책임 | 앱 EXECUTE |
|---|---|---|---|
| 코어 | `008` | 균형 잡힌 분개를 원자적으로 기록 | **없음** |
| 연산 | `009`~`011` | 무엇이 정당한 분개인가 · 누가 할 수 있는가 · 승인이 필요한가 | 있음 |

연산 함수가 계정과 부호를 직접 구성한다. 호출자는 금액과 대상만 넘긴다. **임의 분개를 주입할 인터페이스가 존재하지 않는다.**

### 근거

- 규율(코드 리뷰)이 아니라 권한 설정으로 강제된다
- 인가·승인·멱등이 각 연산의 첫 세 줄에 있어 빠뜨릴 수 없다
- 코어는 여전히 단순하다 — 잠금 순서·해시·잔액·Outbox만 책임진다

### 트레이드오프

연산 하나 추가에 함수 하나가 필요하다. 범용 API보다 손이 많이 간다. 자금을 다루는 시스템에서는 그 비용이 정당하다.

## ADR-014 · 분개 정의표를 문서가 아니라 테이블로 둔다

### 결정

[04-posting-rules.md](04-posting-rules.md)의 각 행을 `ledger.posting_rules(kind, category, account_kind, sign)`에 넣고, `entries` INSERT마다 트리거가 대조한다.

### 근거

"표에 없는 분개를 만드는 코드는 리뷰에서 반려한다"는 사람이 지키는 규칙이다. 사람은 빠뜨린다. 표가 데이터면 DB가 지킨다.

세 겹으로 막는다.

| 겹 | 수단 | 막는 것 |
|---|---|---|
| 1 | `op_*` 함수만 EXECUTE (ADR-013) | 임의 분개 주입 경로 자체 |
| 2 | `entries_posting_rule` 트리거 | 연산 함수 내부 버그 |
| 3 | `v_check_posting_rules` (R7) | 트리거 우회 흔적 |

### 트레이드오프

새 연산을 추가할 때 표에 행을 넣는 것을 잊으면 런타임에 실패한다. 조용히 잘못 기록되는 것보다 낫다.

## ADR-015 · 해시는 분개까지 넣은 뒤 봉인한다

### 맥락

초안은 입력 JSONB에서 다이제스트를 만들어 거래 INSERT 시점에 해시를 확정했다. 두 문제가 있었다.

1. **검증 경로가 기록 경로와 다르다.** 저장된 행에서 다시 계산하려면 별도 코드가 필요하고, 두 벌이 어긋나면 오탐이 난다.
2. **덮는 범위가 좁다.** `actor_staff_id` · `auth_method` · `device_id` · `memo` · `approval_id` · `idempotency_key`가 해시 밖에 있었다. **누가 승인했는지가 체인 밖에 있으면** 감사 추적의 목적인 귀속이 성립하지 않는다.

추가로 `v_now::text`는 `DateStyle` · `TimeZone` GUC에 좌우된다. 세션 설정만 달라도 재계산 결과가 달라진다.

### 결정

- 거래를 `hash IS NULL`로 삽입 → 분개 삽입 → `ledger.canonical_digest(tx_id)`로 계산 → 봉인 UPDATE
- 봉인 UPDATE는 `transactions_seal_guard()`가 **딱 한 번**만 허용한다 (`OLD.hash IS NULL`일 때, 해시 두 컬럼 외 변경 금지)
- 커밋 시점 `hash IS NOT NULL`은 지연 제약 트리거가 보장한다
- 시각은 `to_char(ts AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"')`로 고정

### 결과

기록과 검증이 `canonical_digest()` 하나를 공유한다. `ledger.verify_hash_chain()`이 저장된 행에서 해시를 재계산해 **원문 위조를 탐지한다** — 링크 검사만으로는 잡히지 않는 것이다.

### 트레이드오프

거래당 UPDATE가 한 번 늘고, `transactions.hash`가 `NOT NULL` 제약 대신 트리거에 의존한다. 검증 가능한 체인의 대가로는 싸다.

## ADR-016 · 역분개는 원 `category`를 보존한다

### 맥락

초안은 역분개 분개를 전부 `category = 'reversal'`로 기록했다.

`ddl/013`의 교대 카운터와 윈로스는 `category`로 집계한다. 바이인을 역분개해도 `cash_buyin_shift`가 원래 값 그대로 남는다. **9개 카운터를 파생값으로 승격한 것이 이 설계의 핵심 주장인데, 정정 경로에서 그 주장이 깨진다.**

### 결정

부호만 뒤집고 `category`는 유지한다. 역분개 여부는 `transactions.kind`(`reversal` · `game_cancel`)와 `reverses_tx_id`로 구분한다.

`posting_rules`는 나머지 규칙의 부호를 뒤집어 역분개 규칙을 자동 생성한다.

### 결과

같은 범주의 반대 부호 분개가 합계에서 자동 상쇄된다. 파생 뷰에 특별 처리가 필요 없다.

## ADR-017 · 지점 스코프를 세션 문자열이 아니라 직원 소속에서 얻는다

### 맥락

초안은 `SET LOCAL app.branches = 'HANN,NUSTAR'`를 신뢰했다. 앱이 `'HANN,NUSTAR,ONLINE'`을 써 넣으면 그만이다. 게다가 RLS가 `transactions`와 `games` 두 테이블에만 걸려 있어 `entries`를 조인하면 우회됐다.

### 결정

- `ledger.current_branches()`가 `app.staff_id`를 받아 `identity.staff_branches`를 조회한다
- RLS를 13개 테이블로 확장한다
- 모든 뷰에 `security_invoker = true`를 붙인다 — 정의자 뷰는 소유자 권한으로 실행되어 RLS를 통째로 우회한다

### 트레이드오프 — 한계를 분명히 한다

**RLS는 애플리케이션 버그에 대한 방어선이지, 침해된 `ledger_app` 자격증명에 대한 완전한 방어선이 아니다.** `app.staff_id`를 설정하는 주체가 애플리케이션 자신이기 때문이다.

다만 자유 텍스트와 달리 **실재하는 직원의 실제 소속**만 얻을 수 있고, 사칭한 ID가 `transactions.actor_staff_id`와 `audit.access_log`에 남는다. 완전한 해결은 직원마다 DB 역할을 만드는 것인데 커넥션 풀링과 양립하지 않아 채택하지 않았다.

## 미확정 사항 — 2026-08-15 전건 결정 완료

**U1~U5는 더 이상 미확정이 아니다.** 결정 · 결정일 · 결정자와 각 결정의 코드 근거는 [`docs/spec/00-decisions.md`](../spec/00-decisions.md)에 있다. `AC-20-1`("미확정 항목 각각에 결정 · 결정일 · 결정자가 기록돼 있다. '검토 중'은 결정이 아니다")을 그 문서가 충족한다.

아래는 요약이다. **요약과 결정 대장이 어긋나면 결정 대장이 맞다.**

| # | 항목 | 결정 (2026-08-15 · ungkey) | 이 결정이 만든 작업 |
|---|---|---|---|
| **U1** | 현재 Firestore 데이터가 실거래인가 | **데모다 — 데이터는 이관하지 않는다.** 단 **기능과 스키마는 전부 이식 대상이다** | M5 소멸. 이관 전용 `AC` 6건 소멸, 4건은 성격 변경 |
| **U2** | 다통화 실사용 계획 | **통화별 계정 정식 지원. 환전 연산은 만들지 않는다** | `currencies` 시드 5행. `fx_exchange` 없음 |
| **U3** | 롤링 요율 커미션 계산 규칙 | **관측 롤링 × 요율.** 요율은 게임 개설 시점 스냅샷, **소급 없음** | [`04` §6-1](04-posting-rules.md) 확정. 골든 테스트 착수 가능 |
| **U4** | 지점 확장 계획 | **있다 — `branch_code` ENUM을 폐기하고 `ledger.branches` 참조 테이블로 바꾼다** | M0 첫 스키마 작업. 전 테이블 · 전 RLS · 전 검증 쿼리 |
| **U5** | 규제 관할과 보존 요건 | **유예.** 구조는 M1에 만들고 임계값 · 윈도 · 보존 기간은 `branch_config` 설정값으로 뺀다 | `AC-15-5`만 관할 확정 시점으로 이월 |

### U1의 잔여 위험 — 선언이지 검증이 아니다

"데모다"는 **선언**이며 [07-migration.md](07-migration.md) §1 판별 절차를 돌린 결과가 아니다. 운영 데이터가 뒤늦게 발견되면 이 결정은 무효가 되고 M5가 되살아난다. **오픈 전 한 번은 §1 절차를 돌려 이 선언을 확인할 것** — 비용이 하루다.

### U2의 정확한 의미 — 현행 유지가 아니라 결함 교정이다

현행은 계좌가 `currency:'PHP'` 하드코딩(`index.html:8566`)인데 게임은 5종 통화를 고르게 하고(`index.html:697`) 바이인은 환산 없이 차감한다(`index.html:6939`). `g.cur`는 영수증과 정산 이력에만 흐르고 **잔액 계산에 관여하지 않는다.**

따라서 통화는 **PHP · USD · HKD · CNY · KRW 5종**이다. 이 문서 초안과 `ddl/001` 시드가 3종이었던 것은 현행 UI를 반영하지 못한 것이다.

### U3의 범위 제한 — 파트너 쉐어는 이 결정 밖이다

`share_accrue`에는 현행 구현이 없다(`DR-62`). 쉐어 요율 규칙은 **여전히 미확정**이고 `ddl/001`의 `tx_kind` 블록에 "규칙 미확정 · 실행 경로 없음"으로 남는다. `op_share_settle`은 입력이 금액이므로 U3와 무관하게 만든다.

### U5의 유예는 침묵이 아니다

`AC-20-2`가 요구한 **유예의 명시적 기록**이 [`00-decisions.md`](../spec/00-decisions.md) §6이다. 누적 검사를 끄려면 명시적 센티널을 넣어야 하며 **NULL로 조용히 꺼지지 않는다** — `DR-39`(임계 미지정으로 4-eyes 전체가 침묵 비활성)의 교훈을 같은 자리에서 반복하지 않는다.
