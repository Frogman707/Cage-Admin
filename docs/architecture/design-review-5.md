## 검토 방법

앞선 네 번은 전부 **목표 설계 안쪽**만 봤다 — `ddl/`과 설계 문서가 서로 모순되는지. 이번은 축이 다르다.

`01-current-system.md`는 이 문서 세트의 **사실 기준선**이다. README 전제 1이 그렇게 정한다:

> **현행 구현이 도메인 스펙이다.** `docs/cage-guide/`, `docs/cage-spec/`의 케이지 어드민 기능 정의는 폐기한다.

그렇다면 물어야 할 것은 하나다 — **01이 서술한 현행 기능마다 목표에 대응이 있는가.** 01의 17개 절을 훑으며 각 도메인 사실을 `ddl/`·`04`·`07`에서 역추적했다.

**결과가 앞선 네 번과 다르다. 반증이 발견보다 많다.** 목표 설계는 이 축에서 대체로 충실했다. 새 차단은 없다.

다만 **반증 6건 중 3건은 한 겹 아래에 결함이 있었다.** "대응이 있다"와 "대응이 맞다"는 다른 질문이었다.

## 2. 높음 2건

### DR-61 · `v_shift_counters`의 칩 유입 카운터 2개가 중복 계상한다

**증상.**

01 §9가 교대 카운터 9개를 정의한다. 그중 셋이 NN칩 관련이고, **각각 다른 필드에서 증가한다:**

| 필드 | 증가 지점 | 출처 값 |
|---|---|---|
| `nnChipInShift` | `index.html:7253` | `nn.deposit` |
| `nnCashoutShift` | `index.html:7267` | `nn.cashout` |
| `nnMarkerShift` | `index.html:7271` | `nn.marker` |

**서로소다.** 정산 입력 `nn { deposit, cashout, marker, working }`의 세 필드가 각각 자기 카운터로 간다.

목표 설계의 후계자는 `cage.v_shift_counters`([013](ddl/013_reconciliation.sql))다. 세 카운터의 정의를 보면:

```sql
-- 현행 nnChipInShift · ccChipInShift (금고로 돌아온 칩)
COALESCE((SELECT sum(c.amt) FROM chips c
           WHERE c.branch = s.branch AND c.business_date = s.business_date
             AND c.chip_type = 'nn'), 0)                           AS nn_chip_in_shift,
-- 현행 nnCashoutShift
COALESCE((SELECT sum(c.amt) FROM chips c
           WHERE c.branch = s.branch AND c.business_date = s.business_date
             AND c.chip_type = 'nn' AND c.reason = 'settle_cashout'), 0)
                                                                   AS nn_cashout_shift,
-- 현행 nnMarkerShift
COALESCE((SELECT sum(c.amt) FROM chips c
           WHERE c.branch = s.branch AND c.business_date = s.business_date
             AND c.chip_type = 'nn' AND c.reason = 'settle_marker_redeem'), 0)
                                                                   AS nn_marker_shift,
```

뒤의 둘은 `reason`으로 거른다. **첫 번째는 안 거른다.**

`nn_chip_in_shift`는 그 지점·영업일의 **모든 NN칩 재고 이벤트 합계**다. `settle_cashout`도, `settle_marker_redeem`도, `working_chip_return`도 전부 포함한다. 즉:

```
nn_chip_in_shift ⊇ nn_cashout_shift ∪ nn_marker_shift
```

**세 카운터가 서로소가 아니게 됐다.** `cc_chip_in_shift`도 같다.

**왜 높음인가.**

주석이 등가를 주장한다 — "현행 `nnChipInShift` · `ccChipInShift`". 그런데 현행 필드는 `nn.deposit` 하나에서만 증가한다. **다른 양을 계산하면서 같은 이름을 붙였다.**

세 가지가 겹쳐서 나쁘다.

**① 이관 검증이 이 뷰로 안 된다.** [07-migration.md](07-migration.md) 3-1절 3단계(감사)는 이관 전후 숫자 대조가 전부다. 9개 카운터 중 2개가 구조적으로 다른 값을 내면 그 대조에서 **항상 불일치가 뜬다.** 진짜 이관 오류와 구분할 방법이 없다.

**② 이 뷰의 존재 이유를 정면으로 배반한다.** 01 §9가 현행 문제를 이렇게 쓴다:

> 이 9개 카운터는 서로 독립적으로 누적되며, **상호 정합성을 검증할 수단이 없다.** 하나가 어긋나도 조용히 어긋난다. [03-ledger-model.md](03-ledger-model.md)에서 이 카운터들을 원장 계정과 재고 원장으로 승격해 회계 항등식이 자동 검증하도록 재설계한다.

**정합성을 자동 검증하려고 만든 뷰가 자기 안에서 중복 계상한다.** 항등식을 세우는 순간 안 맞는다.

**③ 3차 DR-42와 같은 자리다.** `chip_inventory_events`에는 R-체크가 없다(DR-42). 그래서 이 뷰의 출력이 틀려도 대사가 잡지 못한다. 두 결함이 같은 테이블에서 겹친다.

**개선 방안.**

`reason` 필터 한 줄. 값은 이미 있다 — `chip_inventory_events.reason`이 `ledger.entry_category`이므로([`005:291`](ddl/005_games_rolling.sql#L291)) `settle_deposit`이 유효한 값이다.

```sql
-- 현행 nnChipInShift · ccChipInShift (정산 입금분만. 캐시아웃 · 마커는 별도 카운터다)
COALESCE((SELECT sum(c.amt) FROM chips c
           WHERE c.branch = s.branch AND c.business_date = s.business_date
             AND c.chip_type = 'nn' AND c.reason = 'settle_deposit'), 0)
                                                                   AS nn_chip_in_shift,
```

그리고 **9개 필드 전부에 대해 같은 검사를 해야 한다.** 이번에 확인한 것은 NN·CC 유입 둘뿐이다. 나머지 7개도 현행 증가 지점과 1:1로 대조해야 한다 — 01 §9의 표가 그 대조표다.

**검증.**

07 3-1절 3단계에 항목으로 넣는다:

```sql
-- 이관 후: 현행 shiftEvents 합산과 v_shift_counters 를 9개 필드 전부 대조.
-- 어느 하나라도 어긋나면 이관 오류이거나 뷰 정의 오류다. 둘을 구분해야 한다.
SELECT * FROM cage.v_shift_counters
 WHERE branch = 'HANN' AND business_date = '2026-08-14';
```

**대사 항등식도 함께 세워야 한다** — `nn_chip_in_shift`가 나머지 NN 카운터들과 어떤 관계여야 하는지가 지금 어디에도 없다. 그게 정의되지 않으면 DR-42의 R9를 만들어도 무엇과 대조할지 모른다.

### DR-62 · 파트너 쉐어 · 롤링 커미션은 현행 구현이 없다

**증상.**

01이 두 곳에서 같은 말을 한다.

[01:90](01-current-system.md) — 계좌 필드 `rate`:

> `rate` — 롤링 요율. 문자열 `"1.45%"` 형태로 저장 (`index.html:5597`). **커미션 계산 코드를 저장소에서 찾지 못했다.** 미구현으로 보인다.

[01:425](01-current-system.md) — 컬렉션 `shareLedger`:

> `shareLedger` | 파트너 | 파트너 쉐어 누계. **데모 시드에서만 쓰이고 실제 적립 코드가 없다**

**저장 구조는 있고 계산 코드는 없다.** 두 도메인 모두.

그런데 목표 설계는 이 도메인에 구조를 만들었다:

| 계층 | 산출물 | 위치 |
|---|---|---|
| 타입 | `tx_kind` `share_accrue` · `share_settle` | `001` |
| 타입 | `account_kind` `partner_share_payable` · `commission_expense` | `001` |
| 분개 규칙 | 4행 | [`004:231-234`](ddl/004_ledger.sql#L231) |
| 컬럼 | `member_profiles.rolling_rate NUMERIC(7,4)` | `003` |
| 쓰기 경로 | `op_open_account`가 그 값을 채운다 | [`011:467`](ddl/011_operations_admin.sql#L467) |
| **계산 규칙** | **없음** | — |

요율 × **무엇** = 얼마인지가 어느 문서에도 없다. [README](README.md) 미확정 사항 3번이 정확히 그것을 묻는다:

> 3. 롤링 요율(`rate`) 커미션 계산 규칙 — 필드는 있으나 계산 코드를 찾지 못함

**왜 높음인가.**

README 전제 1이 이 문서 세트의 헌법이다:

> **현행 구현이 도메인 스펙이다.** … 이 문서 세트의 도메인 사실은 전부 `index.html`, `partner-admin/app.js`, `avatar/app.js`, `shared/*.js`의 실제 코드에서 추출했으며, **각 사실에 코드 위치를 명시한다.**

파트너 쉐어에는 명시할 코드 위치가 없다. 01이 그렇게 확인했다. **그런데 타입 4개와 분개 규칙 4행이 만들어졌다.** 전제를 위반한 유일한 도메인이다.

이게 3차 DR-38에 직접 답을 준다. DR-38은 "`share_accrue`·`share_settle`에 op 함수가 없다"고 지적했다. **왜 없는지가 이제 설명된다 — 만들 근거가 없었다.** 무엇을 계산해 어느 계정에 얼마를 넣을지 아무도 모른다.

따라서 **DR-38의 세 선택지가 등가가 아니다:**

| DR-38 선택지 | 파트너 쉐어에 적용하면 |
|---|---|
| (a) op 7개 추가 | **구현이 아니라 신규 스펙 작성이다.** 요율 규칙을 사업 쪽에서 받아야 한다 |
| (b) 소유자 권한 예외로 선언 | 계산 규칙이 없으므로 소유자도 못 넣는다. 무의미 |
| (c) 타입 삭제 | **README 전제 1과 일치한다.** 규칙이 확정되면 그때 추가 |

**(c)가 기본값이어야 한다.** 지금 (a)를 고르면 코드 근거 없는 도메인을 스키마에 고정하는 것이고, 나중에 실제 규칙이 오면 `posting_rules`와 `account_kind`를 다시 연다 — 그때는 이미 운영 데이터가 있다.

**개선 방안.**

1. **DR-38 결정 문서에 이 사실을 명시한다.** "현행 구현이 없다"는 결정의 입력이지 결과가 아니다.
2. 요율 계산 규칙이 확정되기 전까지 `share_accrue` · `share_settle` · `partner_share_payable` · `commission_expense`와 [`004:231-234`](ddl/004_ledger.sql#L231) 4행을 DDL에서 제외한다.
3. `member_profiles.rolling_rate`는 **유지한다.** 현행에 값이 실제로 저장돼 있으므로(`"1.45%"`) 이관 대상이다. 계산에 안 쓰일 뿐 데이터는 실재한다. 컬럼 주석에 "현행 저장값 보존. 계산 규칙 미확정"이라고 적는다.
4. README 미확정 3번을 **DR-38의 선행 조건**으로 승격한다. 지금은 별개 목록에 있어 연결이 안 보인다.

**이것은 3차 DR-38 · DR-40 · DR-47과 2차 DR-34가 모인 파트너 도메인 묶음의 다섯 번째 조각이다.** 4차 §5가 "미완성 도메인 하나로 설계하라"고 썼는데, 이제 더 정확히 말할 수 있다 — **미완성이 아니라 미착수다. 사업 규칙이 없다.**

## 3. 중간 2건 · 낮음 1건

### DR-63 · 이관 거래의 고정 필드값이 정의되지 않았다 (중간)

`ledger.transactions`는 감사 필드 3개를 강제한다:

```sql
auth_method     identity.auth_method NOT NULL,     -- 004:70
device_id       TEXT NOT NULL,                     -- 004:71
CONSTRAINT tx_actor_required
  CHECK (auth_method = 'system' OR actor_staff_id IS NOT NULL)   -- 004:90
```

`008:287`이 빈 문자열도 거부한다. **이관되는 과거 거래는 이 셋을 채울 수 없다.**

01 §4가 그 이유를 쓴다. `deviceId`는 **Track A 듀얼라이트 배포 시점부터만** 존재한다:

> 신규 필드 3종(`createdAt`/`clientCreatedAt`/`deviceId`)은 … 즉 **듀얼라이트 배포 시점을 경계로 원장 데이터의 성질이 다르다**

M9 그 자체다 — "데이터가 두 시대로 갈린다". 배포 이전 문서에는 `deviceId`가 없고, 행위자도 `staff` 문자열(이름 콤마 결합)뿐이라 `identity.staff.id`로 매핑되지 않는 경우가 생긴다.

답은 있다 — `auth_method='system'`이면 `actor_staff_id`가 면제되고, `device_id`에는 센티널을 넣으면 된다. **문제는 그 결정이 07 어디에도 없다는 것이다.** 07을 전량 grep해도 `device_id` · `auth_method` · 센티널 값에 대한 언급이 없다.

**더 나쁜 것이 하나 있다.** 이관된 거래에 **원본 Firestore 문서 ID를 넣을 컬럼이 없다.** `transactions`에는 `memo TEXT`뿐이다.

M5가 이렇게 쓴다 — "중복 거래 가능성 · 호출 시점 생성 ID · **앱 재시도로 중복 원장 생성됐을 수 있음**". 중복은 이관 후에도 원장에 그대로 남는다. 그때 "이 두 행이 같은 원본에서 왔는가"를 판별할 유일한 근거가 원본 ID다. **memo 문자열 파싱으로 감사하게 된다.**

**개선.** 07에 이관 거래의 고정 필드값을 표로 명시한다.

| 필드 | 이관 시 값 | 근거 |
|---|---|---|
| `auth_method` | `'system'` | `tx_actor_required` 면제 조건 |
| `actor_staff_id` | `NULL` (매핑 가능하면 실제 ID) | 위와 동일 |
| `device_id` | `'migration:<batch-id>'` | `NOT NULL` + 008의 빈 문자열 금지 |
| `idempotency_key` | `'legacy:<원본 문서 ID>'` | 재실행 시 중복 삽입 차단 |
| `kind` | `'opening_balance'` | 3차 DR-38 · 4차 DR-51과 함께 결정 |

`idempotency_key`에 원본 ID를 넣으면 컬럼 추가 없이 원본 추적이 된다 — `UNIQUE`이므로 이관 스크립트 재실행 안전성까지 같이 얻는다. **컬럼을 늘리지 않는 답이 이미 스키마 안에 있다.**

### DR-64 · 지점 분산 출금 폐기 근거가 폐기 대상과 어긋난다 (중간)

[04:79](04-posting-rules.md#L79):

> **지점 분산 출금 폐기:** 현행 `withdrawAcrossBranches()`(`index.html:6428-6443`)는 `MAIN` 계좌 전용 이월 차감 로직이다. 신규 모델에서는 `house_cash`가 지점별 독립 계정이고 **손님 잔액은 이미 통합되어 있으므로** 이 경로 자체가 불필요하다.

폐기 결정 자체는 문제없고, 근거를 단 것도 좋다. **그런데 근거가 다른 질문에 답한다.**

01 §4-4가 서술하는 대상은 **`MAIN` 계좌 전용**이다:

> `MAIN` 계좌 전용 경로다. 지정 지점부터 시작해 `HANN → NUSTAR → ONLINE` 고정 순서로 잔액을 훑으며 부족분을 이월 차감한다.

즉 이 기능이 해결하는 것은 **하우스 현금이 한 지점에서 부족할 때 다른 지점에서 끌어오는 것**이다. 손님 잔액과 무관하다. 04의 근거는 "손님 잔액은 이미 통합되어 있으므로"라고 쓰는데, **손님 잔액 통합은 이 기능이 하던 일이 아니다.**

신규 모델에서 같은 상황이 오면 어떻게 되는가:

1. `op_withdraw`가 `MAIN-HANN`에서 시도 → `house_cash`는 `allow_negative=false`이므로 I2 지연 트리거가 거부
2. 운영자가 `op_branch_transfer`로 `NUSTAR → HANN` 먼저 실행
3. 다시 `op_withdraw`

**한 조작이 두 거래로 나뉘고, 둘 사이는 원자적이지 않다.** 결과는 더 명시적이고 감사 추적도 낫다 — **그래서 좋은 변화일 수 있다.** 문제는 04가 그것을 "불필요하다"고 쓴다는 점이다. 없어지는 게 아니라 **운영자에게 보이는 절차가 바뀐다.**

이 문서 세트에는 그런 변화를 표시하는 관례가 이미 있다. [08-adr.md:362](08-adr.md#L362):

> - 월정산 화면의 "리셋" 동작이 "기간 마감"으로 바뀐다. **사용자에게 보이는 변화가 있다**

**같은 표시가 여기에는 없다.** 그리고 Track A가 이 로직에 테스트를 붙였다는 사실이 무게를 더한다 — `functions/test/spillPlan.test.js`([01:29](01-current-system.md)). 죽은 코드가 아니라 지금 유지보수되는 기능이다.

**개선.** 04:79의 근거를 실제 폐기 대상에 맞게 고치고, UX 변화를 명시한다.

> **지점 분산 출금 폐기:** 현행 `withdrawAcrossBranches()`는 한 지점의 하우스 현금이 부족할 때 다른 지점 잔액을 자동으로 끌어 쓴다. 신규 모델에서는 `house_cash`가 지점별 독립 계정이고 잔액 하한이 강제되므로, 같은 상황을 **`branch_transfer` → `withdraw` 2단계 명시 조작**으로 처리한다. **사용자에게 보이는 변화가 있다** — 자동 이월이 사라지고 운영자가 지점 간 이체를 먼저 승인해야 한다.

그리고 05-api-contract의 현행↔신규 대응표에 `withdrawAcrossBranches` 행을 추가한다. 지금은 표에 없어서 **이 기능이 어디로 갔는지 API 문서만 봐서는 알 수 없다.**

### DR-65 · 데모/실거래 판별 단서가 이미 있는데 쓰이지 않는다 (낮음)

[README](README.md) 미확정 사항 1번이 이 프로젝트에서 가장 큰 미지수다:

> 1. 현재 Firestore 데이터가 실거래인가 데모인가

07-migration.md 전체가 이 답에 걸려 있다. 그런데 **01이 판별 단서를 이미 하나 제공한다.** [01:457](01-current-system.md):

> **데모 시드(`seedDemoData`, `partner-admin/app.js:1800`)만 이 함수를 거치지 않고** `batch.set()`으로 직접 쓴다 — 시드 데이터는 `balanceTotals`에 반영되지 않는다.

즉 **`memberLedger` 항목 중 `balanceTotals`에 반영되지 않은 것은 데모 시드다.** 판별 쿼리 하나로 나뉜다.

07도 README도 이 단서를 참조하지 않는다. 미확정 1번은 여전히 "물어봐야 하는 것"으로 남아 있다.

한계는 분명하다 — 파트너·플레이어 측(`memberLedger`)에만 적용되고, 케이지 측(`ledger`)에는 같은 단서가 없다. 듀얼라이트 이전 데이터도 `balanceTotals`에 없으므로 **시드와 구(舊)데이터가 같은 쪽에 떨어진다.** 그래서 낮음이다.

**개선.** 07 3-1절 1단계(조사)에 이 판별을 항목으로 넣는다. 완전한 답은 아니어도 **범위를 줄인다** — 파트너 측이 전부 시드로 나오면 미확정 1번의 절반은 닫힌다.

## 4. 반증 6건

01의 각 절에서 "목표에 대응이 없을 것"이라고 의심했다가 근거를 찾고 철회한 것들이다. **이번 검토에서는 이쪽이 발견보다 많다.**

| 01의 현행 사실 | 의심 | 반증 근거 |
|---|---|---|
| §4-4 지점 분산 출금 | 목표에 대응 op가 없다 | [04:79](04-posting-rules.md#L79)가 **명시적으로 폐기 결정 + 근거**를 썼다. 누락이 아니라 결정이다 (근거 자체의 문제는 DR-64) |
| §3 KYC 이미지 3종 base64 | 여권 사진만 모델링하고 현장·서명 사진이 빠졌다 | `003`의 `member_profiles`가 **3종 전부** `*_photo_ref` + `*_photo_sha`로 모델링한다. base64 인라인 → 객체 스토리지 키 + 무결성 해시로 승격. [07:123](07-migration.md#L123)이 이관 시 누락 위험도 별도로 기록한다 |
| §10 `{cash,nn,cc}BreakdownCounts` 권종별 매수 | 원장으로 승격하며 권종 정보가 소실된다 | `006`의 `balancing_counts.denomination_counts JSONB`가 **현행 구조를 그대로 유지**한다(`{"1000": 25, ...}`). `variance_minor` 생성 컬럼과 4-eyes CHECK까지 추가됐다 |
| §6 `rollingEvents.memo` 7종 | `source` 승격에서 일부 값이 누락된다 | [`001:155-163`](ddl/001_types_and_extensions.sql#L155) `cage.rolling_source`가 **7종 전부 + `correction`**을 담고, 각 값에 원 memo 문자열을 주석으로 붙였다. M2의 "빈 문자열 = `'rolling'`" 모호성도 `manual`로 해소 |
| §9 교대 카운터 9개 | 일부 필드가 파생 뷰에 없다 | `cage.v_shift_counters`가 **9개 전부** 매핑한다. 각 컬럼에 현행 필드명 주석까지 있다 (단 2개가 다른 값을 계산 — DR-61) |
| §13-2 `correction` 카테고리 | 목표에 대응 kind가 없다 | [04:552](04-posting-rules.md#L552)가 명시한다 — "현행 `correction`(라운드 취소 환불·회수)은 신규 모델에서 `reversal`이 대신하되, 원 `category`를 유지한다" (실행 경로 부재는 4차 DR-50) |

### 반증에서 배운 것

**여섯 중 셋은 한 겹 아래에 결함이 있었다.**

| 반증 | 한 겹 아래 |
|---|---|
| 분산 출금 — 폐기 결정이 있다 | 근거가 폐기 대상과 다른 질문에 답한다 (DR-64) |
| 교대 카운터 — 9개 전부 매핑됐다 | 2개가 다른 양을 계산한다 (DR-61) |
| `correction` — `reversal`로 매핑됐다 | 그 `reversal`을 부를 경로가 없다 (4차 DR-50) |

**"대응이 있는가"와 "대응이 맞는가"는 다른 질문이다.** 앞선 네 번의 검토는 전자만 물었다. 커버리지 표는 세 경우 모두 초록색으로 칠해진다.

다음 검토는 매핑 표의 각 행에 대해 **양쪽 수식을 나란히 놓고 같은지 확인**해야 한다. 이름이 같다는 것은 근거가 아니다.

## 5. 앞선 등록부와의 연결

### DR-62가 3차 DR-38의 결정을 바꾼다

4차 §6은 DR-38을 "3번 묶음의 결정"으로 놓고 세 선택지를 등가로 제시했다. **DR-62가 그 등가를 깬다.**

파트너 쉐어에 한해 (a)안은 구현이 아니라 **신규 사업 규칙 작성**이다. 요율 계산이 무엇인지 아무도 모르고, 현행 코드에도 없고, 01이 그것을 확인했다.

따라서 착수 순서의 3번 묶음이 이렇게 갈린다:

| 도메인 | DR-38 선택 | 근거 |
|---|---|---|
| 온라인 베팅 (`bet`·`payout`) | **(a) op 추가** | 현행 구현 있음 — `shared/game-engine.js:96`·`:111` |
| 포인트 (`point_earn`·`point_convert`) | **(a) op 추가** | 현행 구현 있음 — 01 §13-3에서 category 확인 |
| 마이그레이션 (`opening_balance`) | **(a) op 추가** | 07이 요구한다. 없으면 이관 자체가 불가 |
| **파트너 쉐어** (`share_accrue`·`share_settle`) | **(c) 타입 삭제** | **현행 구현 없음.** DR-62 |

**하나의 결정이 아니라 도메인별 네 개의 결정이다.** 그리고 넷 중 셋은 이미 답이 정해져 있다 — 코드가 있으니까.

### 파트너 도메인 묶음이 완성됐다

4차 §5까지 네 조각이었다. 이제 다섯이다:

| 항목 | 층 | 상태 |
|---|---|---|
| 2차 DR-34 | 권한 | 파트너 투표 권한이 카탈로그에 없다 |
| 3차 DR-40 | 계층 | 순환 참조를 막지 않는다 |
| 3차 DR-47 | 주체 | 파트너 타입 검증이 FK뿐이다 |
| 3차 DR-38 | 자금 | 쉐어 op 함수가 없다 |
| **5차 DR-62** | **사업 규칙** | **계산 규칙 자체가 없다** |

**아래에서 위로 읽어야 한다.** DR-62가 맨 아래다. 사업 규칙이 없으면 자금 연산을 정의할 수 없고, 자금 연산이 없으면 권한도 계층 제약도 무엇을 보호하는지 모른다.

4차 §5는 "미완성 도메인 하나로 설계하라"고 썼다. **정정한다 — 미착수 도메인이다.** 설계를 시작할 입력이 아직 없다. 착수 순서 7번은 "일괄 설계"가 아니라 "사업 규칙 수집"으로 바뀌어야 한다.

### DR-61이 3차 DR-42와 겹친다

DR-42는 `chip_inventory_events`에 R-체크가 없다고 지적했다. DR-61은 그 테이블을 읽는 뷰가 중복 계상한다고 지적한다.

**둘을 함께 고쳐야 한다.** R9를 만들 때 대조 항등식이 필요한데, 지금은 카운터 간 관계가 정의돼 있지 않다. DR-61을 고치면 서로소 관계가 회복되고, 그러면 R9가 세울 항등식이 생긴다:

```
칩 재고 순증 = 발행 − (정산입금 + 캐시아웃 + 마커리딤 + 워킹칩반환)
```

**DR-61이 DR-42의 선행 조건이다.** 착수 순서 4번(게임 도메인) 안에서 순서를 정해야 한다.

## 7. 이 문서에 대해

### 이번 검토가 앞선 넷과 다른 점

발견 5건, 반증 6건. **네 번 중 처음으로 반증이 더 많다.**

이유는 축이 달라서다. 앞선 네 번은 목표 설계의 **내부 일관성**을 봤고 — 선언과 구현, 규칙과 강제, 타입과 함수 — 거기서는 계속 빈칸이 나왔다. 이번은 **현행과의 대응**을 봤고, 여기서는 목표 설계가 충실했다.

**두 결과가 모순이 아니다.** 01을 기준선으로 삼는 규율은 잘 지켜졌다. 지켜지지 않은 것은 그 아래 — 기준선에서 뽑은 요구사항을 실제로 실행 가능한 함수와 권한으로 만드는 층이다. 3차 DR-38, 4차 DR-50, 5차 DR-62가 전부 그 층이다.

**요구사항 수집은 잘했고 구현 경로 완결성 검사를 안 했다.** 다섯 번의 검토를 한 문장으로 줄이면 그것이다.

### 검증하지 않은 것

- **`v_shift_counters`의 나머지 7개 필드.** DR-61은 NN·CC 유입 둘만 확인했다. 나머지도 01 §9 표와 1:1 대조해야 한다. **7개 중 몇 개가 더 틀렸는지 모른다**
- **파트너·플레이어 측 24종 컬렉션.** 01 §13-1이 목록만 준다. 각각의 목표 대응은 [00-system-map.md](00-system-map.md) §8 A1로 미뤄져 있고, 이 검토는 거기까지 가지 않았다
- **여전히 실행 검증 0건.** 다섯 번째 등록부에서도 1차 DR-12(골든 테스트 없음)가 같은 자리에 있다. DR-61은 **뷰를 한 번 실행하면 5초에 확인된다** — `nn_chip_in_shift ≥ nn_cashout_shift + nn_marker_shift`가 항상 성립하는지만 보면 된다

### 남은 미독

`references.md`(4차에서 확인 완료)를 빼면 설계 문서 세트는 전량 읽었다. 남은 것은 **저장소 코드 자체**다 — 01이 인용한 `index.html` 9,422줄, `partner-admin/app.js` 1,867줄, `avatar/app.js` 1,202줄.

01의 서술이 코드와 맞는지는 **한 번도 검증하지 않았다.** 이 문서 세트 전체가 01을 사실 기준선으로 삼는데, 그 기준선 자체는 검토 대상이 아니었다. 여섯 번째 축이 있다면 그것이다.

**65건이 전부라는 뜻이 아니다.**
