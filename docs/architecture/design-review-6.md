## 2. 차단 — DR-66: 롤링 커미션 정산 흐름이 설계에 없다

### 코드에 있는 것

`settleGame()` → `_doSettleGame()` (`index.html:7218-7267`, 최초 커밋 9a1c559 2026-08-01부터 존재):

1. 정산 대상 게임 선택, PIN 재인증 (`requestPinAuth`)
2. **커미션 수동 입력** (`#settleRolling`), F&B 차감액 입력, 최종 지급액 `result` 산출
3. `result > 0`이면 **계좌에 입금** — `applyAccountTransaction(g.account, 'IN', result, memoRollingSettle)` (`:7241`)
4. `DB.settled`에 정산 레코드 push — `{gameId, account, branch, dt, buyin, cashout, winLoss, rolling, commission, fb, result, staff}` (`:7250`)
5. 텔레그램 통지 + 영수증 렌더 + 이벤트 커미션 트리거 (`:7259`)

리포트가 이 데이터에서 파생된다 — `reportCommissionPaid()` (`:8142`), `computePeriodMetrics()`의 `rollingCommPaid` (`:8144`).

### 설계에 없는 것

| 계층 | 상태 |
|---|---|
| `01` §7 | 중간정산(7-1)·게임종료(7-2)만 서술. 롤링 커미션 정산 절 자체가 없다 |
| `04` | §6 "롤링 입력 — 자금 이동 없음"뿐. **정산 지급은 자금 이동인데** 분개 규칙 없음 |
| `05` | games 엔드포인트 6종(create/buyin/rolling/mid-settle/end/cancel)에 정산 없음 |
| DDL | `cage.settlement_kind` = `'mid'`·`'final'`뿐. 커미션 지급 `tx_kind` 없음. `commission_expense` 계정은 §13-3 파트너 쉐어에만 연결 |

### DR-62와의 관계 — 5차 판정 일부 정정

5차 DR-62는 `01:90`("커미션 계산 코드를 저장소에서 찾지 못했다")을 근거로 롤링 커미션을 "현행 구현 없음"으로 분류했다. **절반만 맞다.** `rate` 필드 기반 **자동 계산**은 실제로 없다 — 01:90의 서술 자체는 참이다. 그러나 **수동 입력 지급 흐름은 있고, 매 정산마다 실제 돈이 계좌로 들어간다.** 01이 이 흐름을 서술하지 않아 5차는 "계산 코드 없음 = 지급 없음"으로 읽었다.

따라서 DR-38 4분할 표가 다시 바뀐다:

| 도메인 | 5차 판정 | 6차 정정 |
|---|---|---|
| 베팅 `bet`·`payout` | (a) op 추가 | 유지 |
| 포인트 | (a) op 추가 | 유지 — 단 DR-68: 케이지 포인트는 별도 결정 |
| `opening_balance` | (a) op 추가 | 유지 |
| **롤링 커미션** | — (미분류) | **(a) op 추가** — 수동 입력 지급이 현행 스펙. `rate` 자동 계산은 여전히 미확정(README 미확정 3) |
| 파트너 쉐어 | (c) 타입 삭제 | 유지 — `share_accrue`에는 여전히 현행 구현 없음 |

### 필요한 것

- `tx_kind`에 `commission_payout`(또는 기존 값 재사용 결정) + 분개 규칙: 차변 `commission_expense[branch]` / 대변 `guest[account]`
- `POST /v1/games/{game_no}/settle` — 커미션·F&B·지급액, 멱등키 `settle:{game_no}:{seq}`
- `cage.game_settlements` 확장 또는 별도 테이블 — `commission`·`fb`·`result`·`staff` 보존 (현행 `DB.settled` 대응)
- `cage.op_settle_commission()` + GRANT

검증 쿼리(구현 후): `SELECT count(*) FROM ledger.posting_rules WHERE kind='commission_payout'` — 0이면 이 결함 재발.

## 3. 높음

### DR-67: 이벤트 커미션 — 계산식 있는 실자금 이동, 설계 부재

`payEventCommissionForSettle()` (`index.html:9062-9078`, c749806 2026-08-02 자동화):

```js
const amt = Math.round(rolling*rate/100);      // :9065 — 계산식이 있다
const txn = await applyAccountTransaction(account, 'IN', amt, t('memoEventCommission'));  // :9067
```

- 활성 기간 관리: `DB.eventStart/eventEnd/eventRate`, 활성화 로그(`eventActivationLog`), 지급 이력(`eventHistory`) (`:9001-9060`)
- 매 롤링 정산마다 자동 트리거 (`:7259`)
- 01·04·05·DDL 전부 부재. 리포트의 `eventComm` 항목(`:8158`)도 이 데이터에서 파생

이건 01:90의 반례이기도 하다 — "커미션 계산 코드를 찾지 못했다"지만 **이벤트 커미션은 계산식이 있다.** 필요한 것: 이벤트 기간 엔티티(활성 구간·요율·활성화 감사), 분개 규칙, 정산 트리거 시 자동 지급 규약.

### DR-68: 케이지 포인트 ≠ 파트너 포인트 — 설계는 한쪽만

`grantPoints()`/`usePoints()` (`index.html:8958-8991`):

- 대상: **케이지 계좌**(SE7419류). `DB.pointsByAccount`·`DB.pointsHistory`, localStorage 전용
- `memberLedger`를 거치지 않는다 — 파트너/플레이어 측 `point_earn`·`point_convert`(`04` §13-2의 근거)와 **주체도 저장소도 다른 별개 시스템**
- 01에는 케이지 포인트 절이 없다 (§ 목록에 부재). 00 커버리지 매트릭스 "포인트 · 파트너 쉐어" 행은 `partner-admin/`만 가리킨다
- 7개 네비 뷰 중 하나(`points`)가 통째로 이 시스템이다

결정 필요: 케이지 포인트를 (a) `04` §13-2 회계 주체로 흡수(회원=손님 매핑 전제 — 현재 매핑 없음), (b) 별도 `point` 계정 종류로 분리, (c) 폐기. 어느 쪽이든 **현행 잔액(`pointsByAccount`) 이관 규칙이 필요하다** — DR-71과 연결.

## 4. 중간 · 낮음

### DR-69 (중간): 컨시어지 도메인 전체 미설계

`bookHotel`/`reserveCar`/`requestAero` + 각 취소·영수증·렌더 (`index.html:8774-8932`). 자금 무관, localStorage 전용, 알림 연동. 01은 §전체에서 프록시 CORS 한 줄(`:535`)만 언급. 00 커버리지 매트릭스에 행 자체가 없다 — "어디가 설계 안 됐는지" 보여주는 문서가 이 도메인은 **누락 여부조차 기록하지 않았다.** DDL·API 없음. 예약 데이터는 손님 응대 기록이므로 최소 테이블 3개(hotel_bookings·car_reservations·flight_assists) + CRUD 엔드포인트 필요. 자금 원장과 무관하므로 `cage` 스키마 밖(예: `concierge`)이 자연스럽다.

### DR-70 (중간): 계좌 차단 — 상태값은 있고 경로가 없다

`applyBlock()`/`unblock()` (`index.html:8608-8626`): 사유·직원·일시 기록, PIN 없이 실행, `unblock`은 `splice` **삭제** — 해제 이력이 소멸한다. 목표 측: `ledger.account_status`에 `'suspended'`가 있으나(001:69) — 상태를 바꿀 op 함수도, `PATCH /v1/accounts/{code}`의 범위(05:203 "KYC 수정 (자금 무관)")에도 차단이 없다. 4차 DR-50과 같은 패턴 — **타입은 선언했고 경로를 안 만들었다.** 차단·해제는 감사 대상 조작이므로 이력 테이블 + 재인증 요구가 필요하다.

### DR-71 (중간): localStorage 전용 업무 데이터 이관 계획 부재

07 M11은 `accounts`만 다룬다. 같은 처지의 데이터가 더 있다:

| `DB.*` 키 | 내용 | 성격 |
|---|---|---|
| `settled` | 롤링 정산 이력 (커미션·F&B·지급액·직원) | **자금 이력** — DR-66 |
| `pointsByAccount` · `pointsHistory` | 케이지 포인트 잔액·이력 | **잔액** — DR-68 |
| `correctionLog` | 회원사 차액 정정 이력 (PIN 재인증 조작) | 감사 이력 |
| `eventHistory` · `eventActivationLog` · `eventStart/End/Rate` | 이벤트 지급 이력·설정 | 자금 이력 — DR-67 |
| `hotels` · `cars` · `aero` | 컨시어지 예약 | 업무 기록 — DR-69 |
| `blocks` | 계좌 차단 목록 | 상태 — DR-70 |
| `notifications` | 인앱 알림 60건 | 휘발성 — 이관 불요 판정만 기록하면 됨 |

M11의 네 가지 문제(개시 대상 부재·단말 간 불일치·정본 판별 불가·용량 한도)가 전부 그대로 적용된다. 각 항목에 이관/폐기 판정 한 줄씩이라도 07에 있어야 한다.

### DR-72 (낮음): 설계 문서의 코드 라인 참조가 HEAD와 어긋난다

워킹트리는 clean — 코드는 HEAD 그대로인데 참조가 어긋난다: 01 §7-1 "`_doConfirmMidSettle` (`index.html:7219-7298`)" — 현재 7219는 `settleGame`이고 실제 `_doConfirmMidSettle`은 `:7348`. 04 §7-4 "`g.checkpoints` 배열(`index.html:7241`)" — 현재 7241은 `_doSettleGame`의 계좌 입금 행이다. 어긋난 폭 ≈ 정산 블록(7218-7341) 크기. **01 작성 시 정산 블록을 건너뛰고 라인을 센 흔적** — DR-66과 같은 뿌리다. 05:122-173의 참조들도 같은 폭으로 검증 필요.

## 5. 연동 대 재구현 판정

사용자 질문 셋에 대한 답.

### 5-1. 기능·스키마가 설계에 반영됐는가

**자금 코어는 반영됐고, 주변 도메인 다섯이 빠졌다.** 입출금·이체·지점이체·게임(시작/바이인/중간정산/종료/취소)·롤링 입력·메인케이지·실사·교대·직원 인증은 코드→01→04→05→DDL 사슬이 이어진다(1~5차에서 사슬 내부 결함 65건은 별도). 끊긴 곳: 롤링 커미션 정산(DR-66)·이벤트 커미션(DR-67)·케이지 포인트(DR-68)·컨시어지(DR-69)·계좌 차단(DR-70). 다섯 중 둘은 실자금 이동이다.

### 5-2. 프로토타입과 연동하는 것이 맞는가

**이행기 전술로만 맞다.** 프로토타입의 데이터 계층은 "로컬 낙관 변경 → 배경 동기화"다: 전 함수가 `DB.*` 동기 변경 + `saveDB()` + 즉시 렌더를 인라인으로 수행하고, ID는 `Math.random()`, 시각은 클라이언트 시계(`phNow`), 잔액 검사는 메모리 변수다. 목표 설계는 정확히 이 전부를 반전시킨다 — 서버 확정 응답·서버 ID·서버 시각·DB 강제 잔액. 이 반전은 어댑터 한 겹으로 흡수되지 않는다. 쓰기 경로가 `applyAccountTransaction` 등 ~10개 함수로 수렴하는 건 사실이지만, **낙관 변경을 전제로 짜인 호출부 수백 곳이 전부 비동기 확정 대기로 바뀌어야 한다.** 9,422줄 단일 파일, UI 테스트 0에서 그 개조는 사실상 재작성이다.

프로토타입의 역할: **기능 정본(스펙)으로 유지.** 화면 구성·조작 흐름·재인증 UX는 README "바꾸지 않는 것" 그대로 새 구현의 수용 기준이 된다. Track A(현행 하드닝)가 이행기 동안 실자금을 지키는 완충이라는 기존 구도도 유지.

### 5-3. 재구현 프레임워크

**Vite + React SPA 권장. Next.js는 불요.**

| 근거 | 판단 |
|---|---|
| 내부 도구 — SEO·공개 랜딩 없음, 전 화면 인증 뒤 | SSR/RSC 이점 소멸 |
| 실시간 8채널 WebSocket + 명령 API (`02`) | 클라이언트 상태 중심 — SPA 자연스러움 |
| `02` 목표 배포 구조 — API 게이트웨이 분리 | 프론트는 정적 산출물이면 충분. Next 서버 런타임은 운영 표면만 늘린다 |
| 현행 구조 — 뷰 7개·모달 수십·전역 상태 하나 | 라우터 + 상태 관리 + 컴포넌트 분해로 1:1 이식 가능 |
| `shared/i18n.js`·테마 | 그대로 이식 가능한 모듈 이미 존재 |

이식 순서는 화면 단위 스트랭글러가 가능하다 — 자금 화면(accio·game·balancing)부터 새 SPA로, 컨시어지·포인트·리포트는 후순위. 파트너 콘솔(58화면)·플레이어 앱은 A1·A2 보류가 풀린 뒤 같은 판정을 적용한다.

**단, 순서가 있다.** 재구현 착수 전에 차단 13건 — 특히 이 라운드의 DR-66(정산 op 부재)과 4차 DR-50(역분개 경로 부재) — 이 해소돼야 한다. 프론트가 호출할 엔드포인트가 없는 상태에서 화면부터 만들면 프로토타입의 "서버 없는 기능"을 재생산하게 된다.

## 6. 착수 순서 (72건 통합)

1~5차 순서에 6차를 삽입한 변경분만:

1. **기준선 수정이 최우선이 됐다** — 01에 §7-0(롤링 커미션 정산)·이벤트 커미션·케이지 포인트·컨시어지·차단 절 추가 (DR-66~70의 서술 근거). 기준선이 틀린 채로 나머지를 고치면 같은 공백이 재발한다.
2. DR-66: `04`에 분개 규칙 + `05`에 정산 엔드포인트 + DDL(`tx_kind`·규칙 행·op 함수·GRANT) — 4차 DR-50(역분개)과 같은 묶음으로.
3. DR-67·DR-68: 사업 결정 수집(이벤트 커미션 지속 여부, 케이지 포인트 처리 방침) — 5차의 "파트너 쉐어 사업 규칙 수집"과 같은 회의에서.
4. DR-71: 07에 localStorage 데이터 항목별 이관/폐기 판정 표 추가.
5. DR-69·DR-70: 자금 무관 — 재구현 화면 이식 순서에 맞춰 후순위.
6. DR-72: 01·04·05 라인 참조 일괄 재검 — 1번과 같은 편집 세션에서.

**이 라운드가 바꾼 것:** 1~5차의 종합("요구사항 수집은 잘했고 구현 경로 완결성 검사를 안 했다")에 한 층이 추가됐다 — **요구사항 수집도 케이지 어드민의 주변 도메인 다섯을 놓쳤다.** 01은 자금 코어에 대해선 정확했고(반증 4건), 코어 밖에서 침묵했다. 침묵은 커버리지 표에 나타나지 않는다 — 5차의 교훈("대응이 있는가 ≠ 대응이 맞는가")에 이어, 6차의 교훈은 **"서술이 없으면 대조 자체가 일어나지 않는다"**이다.
