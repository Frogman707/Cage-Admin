## 2. DR-73

### 포인트·쉐어 연산의 실행 계층이 어느 계획에도 없다 — **높음**

`point_earn` · `point_convert` · `share_accrue` · `share_settle` 4종은 설계의 **세 계층이 완성**되어 있다:

| 계층 | 위치 | 상태 |
|---|---|---|
| 타입 | [`ddl/001:88-91`](ddl/001_types_and_extensions.sql) `tx_kind` 4종 | ✅ |
| 계정 | [`ddl/003:54-56`](ddl/003_accounts.sql) `player_wallet` · `player_points` · `partner_share_payable` | ✅ |
| 분개 | [04 §13-2·§13-3](04-posting-rules.md) — "아바타 영향을 받지 않으므로 먼저 확정한다" | ✅ |
| RBAC 권한 | [`ddl/002:145-146`](ddl/002_identity.sql) `('partner_admin', 'member.point_earn')` · `'member.point_convert'` | ✅ (포인트만) |
| **op 함수** | `009`~`011` 전수 — `op_point_*` · `op_share_*` **없음** | ❌ |
| GRANT | `012` — 부여할 대상 함수가 없음 | ❌ |

[ADR-013](08-adr.md) 구조상 `ledger_app`은 op 함수 EXECUTE만 가능하다 — **op가 없으면 이 4종 분개는 어떤 권한으로도 만들 수 없다.** `002`가 포인트 2종의 권한 문자열까지 정의한 상태라 부여할 함수만 비어 있다 (쉐어 2종은 권한 행도 없다).

계획 항목 어디에도 배정되지 않았다:

- [00 §8](00-system-map.md) **A4**(원장 카테고리 — 포인트·쉐어)는 ✅ **완료**로 닫혔다 — 완료된 범위는 타입·계정·분개까지고, 실행 계층은 완료 판정에 포함되지 않은 채 항목이 닫혔다.
- 보류 산출물 목록([07:376-377](07-migration.md))은 `ddl/015_operations_player.sql`만 계획한다 — **플레이어** 연산이다. 포인트·쉐어는 "파트너 콘솔 측이라 아바타 영향 없음"([00:379](00-system-map.md))이므로 보류로도 커버되지 않는다.
- **A8**(플레이어·파트너 API)은 "05 §3·§4에 엔드포인트 0개"로 기술 — API 계약 계층이지 op 계층이 아니다.

`DR-50`(역분개 경로 부재) → `DR-70`(차단 op 부재) → `DR-66`(정산 설계 부재)과 같은 뿌리의 **4번째 재발**이다. 이번 특이점: 결함 추적 장치(00 §8) 자체가 해당 항목을 완료로 닫아 **공백이 추적 밖에 있다.**

**필요 조치:**
1. `op_point_earn` · `op_point_convert` · `op_share_accrue` · `op_share_settle` — `009` 확장 또는 신규 파일. `op_share_settle`은 요율 규칙(U3)과 무관하게 만들 수 있다 — 입력이 금액이지 요율이 아니다.
2. `002`에 쉐어 권한 2행 추가, `012`에 GRANT 4행 추가.
3. `00` §8 A4를 재개하거나 신규 항목(예: A10 — 파트너 측 op 계층)으로 등록. **A8 착수 조건에 op 계층을 명시**해야 엔드포인트를 만들고 나서 호출할 함수가 없는 상황을 막는다.

## 3. 중간 2건

### DR-74 — 요청 승인 워크플로가 "엔드포인트 0개"로 축소 기술 — **중간**

현행 파트너 콘솔의 승인 흐름 2종은 **상태 전이와 기장이 분리**되어 있다:

- `approveDeposit` ([partner-admin/app.js:890-906](../../partner-admin/app.js)) — Firestore 트랜잭션으로 `status: '대기'→'승인'` 전이(:894-900), **기장은 트랜잭션 밖**(:906).
- `processPayment` ([:1661-1683](../../partner-admin/app.js)) — 같은 구조 (:1668-1674 전이, :1681 기장).

실패 창: 상태 커밋 후 기장 실패 시 **요청은 '승인'인데 회원 잔액 변동이 없고**, 재시도하면 `ALREADY_PROCESSED`로 거부된다 — 수동 복구 외엔 경로가 없다. [01 §13-5](01-current-system.md)는 "트랜잭션이 지키는 것은 status이지 잔액이 아니다"까지만 서술하고, `P-01`~`P-14`에도 이 창은 등록되어 있지 않다.

목표 설계 쪽: `depositRequests` · `paymentRequests`에 대응하는 **요청 테이블이 목표 스키마에 없고**, A8은 "엔드포인트 0개"라는 목록 결손으로만 기술한다. 요청→승인은 엔드포인트 나열보다 큰 설계 단위다.

**필요 조치 (A8 착수 시):** 요청 엔티티 + 승인 = **단일 op** (상태 전이 + 분개 한 트랜잭션) + 멱등키 자연키(`deposit_req:{request_id}`) + 금액 임계 시 4-eyes 연동(`require_approval_if_over_threshold` 재사용). 현행 2단계 구조를 이식하면 안 된다는 요구를 지금 명시한다.

### DR-75 — 온라인 회원 주체 모델의 소속 항목 미지정 — **중간**

목표 스키마의 "회원"은 **케이지 손님**이다:

- [`ddl/003:183-212`](ddl/003_accounts.sql) `ledger.member_profiles` — 여권·현장사진·`rolling_rate`("1.45%") 등 **케이지 `accounts` 대응 필드**뿐이다.
- [`ddl/001:40`](ddl/001_types_and_extensions.sql) `party_type 'member'` 주석 — "현행 accounts 중 isMain=false". 케이지 한정.

반면 `account_kind 'player_wallet'`("현행 memberLedger", [`003:54`](ddl/003_accounts.sql))은 존재한다 — **온라인 회원의 돈 계정은 정의됐는데 그 소유 주체가 어느 party인지 규칙이 없다.** 케이지 손님(SE7419)과 온라인 회원(`members/SEN1001`)이 같은 party인지, 대응(매칭) 규칙은 무엇인지 미정 — [04 §12](04-posting-rules.md) `wallet_transfer`는 둘의 연결을 전제하는 신규 기능이다.

`members` 컬렉션의 나머지 실체도 목표에 없다: `memberType` 4종(정회원/준회원/관리회원/멀티회원), `status` 3종(정상/정지/블랙리스트), `smsVerified`, `parentAgent`(소속이동), `betMax`/`betMin`, `pw`/`withdrawPw`(평문 → identity 이전 대상). [02:51](02-target-architecture.md)이 Identity 스코프에 "회원 인증"을 선언했지만 `002`에 회원 인증 테이블은 없다.

**소속이 모호하다:** 회원 로그인·베팅은 플레이어 도메인(A1 보류)이지만, 정지·블랙리스트·정회원 전환·소속이동·SMS 인증은 **파트너 콘솔 운영 기능**(A8 "착수 가능")이다. 어느 항목이 회원 주체 설계를 갖는지 지정돼야 A8이 진행될 수 있다.

**필요 조치:** `00` §8에 소속 결정 기록 — 권고: 주체·상태·인증은 A8(파트너·아바타 무관), 게임 참여 이력은 A1. `member_profiles`와 온라인 회원 프로필의 분리/통합은 ADR로.

## 5. 반증 — 파트너 측 기준선은 건전하다 (6건)

6차(케이지)와 대조적으로, 파트너 측은 기준선·자기결함등록이 코드와 일치한다:

1. **[01 §13-2](01-current-system.md) 자금 쓰기 지점 9곳 — 줄번호 전부 실코드 일치.** `:416` · `:906` · `:1304` · `:1307` · `:1681` · `game-engine.js:76`/`:96`/`:111` · `avatar/app.js:714` 모두 확인. 6차 DR-72(케이지 줄번호 스테일)와 대조된다.
2. **01 §13-1 컬렉션 24종 — 코드 참조와 일치.** 이탈 0.
3. **`'transfer'` 사각지대는 이미 문서화됐다.** 월렛이체리스트가 존재하지 않는 카테고리를 필터해 상시 공백인 사실 — [reference-screens.md:187](../partner-admin/reference-screens.md) "transfer 카테고리를 쓰는 코드는 저장소 어디에도 없습니다."
4. **`P-01`~`P-14` 전부 실재 확인.** admin/0000 폴백 로그인(:185), `onclick` 문자열 보간 XSS, 라운드 취소 환불 루프 비원자(:1299-1310), 결과 수정 미재정산(:1258-1263) 등 — 코드 재확인 결과 등록 내용과 일치.
5. **`partnerStaff` 평문 노출은 06에 행이 있다.** [06:38](06-security.md) + 최저비용 조치 명시(06:514).
6. **아바타 보류는 재개 조건이 명시돼 있다.** [07:373-374](07-migration.md) "아바타 개선이 확정되면 그 문서가 갱신된 뒤 설계를 착수한다" — §6의 외부 확인과 부합.

## 7. 착수 순서 반영 (77건 통합)
