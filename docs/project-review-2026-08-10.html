01총평

이 프로젝트는 제품 표면(UI · 화면 흐름 · 도메인 모델링)의 완성도가 높습니다. 케이지 원장, 교대, 롤링, 메인 케이지, 파트너 정산, 플레이어 베팅과 로드맵까지 실제 카지노 운영 도메인이 상당히 정밀하게 구현되어 있고, 5개 국어 i18n과 TOTP 기반 2단계 인증 같은 요소도 이미 들어가 있습니다. 영업 시연물로서 보여줄 것은 충분히 갖췄습니다.

반면 그 뒤를 받치는 신뢰 경계는 아직 존재하지 않습니다. 브라우저가 Firestore에 직접 쓰는 구조인데 Firestore 보안 규칙 파일이 저장소에 없고, 인증 · 잔액 검사 · 라운드 결과 · 페이아웃 계산이 전부 클라이언트 권한입니다. 저장소 전체에서 runTransaction 0건, 클라이언트 serverTimestamp 0건입니다. 즉 "브라우저를 신뢰하지 않으면 성립하는 기능"이 현재 하나도 없습니다.

핵심 판단

발견된 21건 중 대부분은 "서버 권한 계층이 없다"는 단 하나의 원인에서 파생됩니다. 개별 항목을 하나씩 패치하는 접근은 비효율적이며, 서버 API 계층을 도입하는 순간 함께 해소됩니다. 따라서 이 보고서는 각 항목을 "지금 데모에서 고칠 것"과 "서버 전환 시 자연히 해소될 것"으로 구분해 표기합니다.

데모 용도로 지금 당장 처리해야 할 것은 4건입니다 — 공개 번들에 커밋된 API 비밀값(S2), 주석에 남은 마스터 비밀번호 평문(S8), 기본 거부 Firestore 규칙 부재(S1), 파트너 콘솔 저장형 XSS(S7). 나머지는 서버 API 전환 계획에 흡수시키는 편이 합리적입니다.

P0 S1 Firestore 보안 규칙 파일 부재

저장소 전체 · firebase.json

저장소에 *.rules 파일이 0건이고, firebase.json에 firestore 섹션이 없습니다. 즉 규칙은 배포 파이프라인에 존재하지 않으며, 나중에 규칙을 작성해도 현재 CI로는 자동 배포되지 않습니다.

   테스트 모드 규칙
        │
        ├── 만료일 도달 ────► allow: if false  ──► 앱 전면 무음 정지
        │                                          (빈 catch 29곳 때문에
        │                                           사용자에게 표시조차 안 됨)
        │
        └── 만료 전 ───────► allow: if true   ──► DB 전면 공개
                                                   ↓
                        projectId 는 클라이언트 번들에 노출 (cage-ui.js:11)
                                                   ↓
                        누구나 Firestore SDK 로 직접 접속 가능

공개 상태일 경우 가능한 것: members 전량 읽기로 전 회원 평문 비밀번호 · 출금 비밀번호 획득, accounts의 여권번호 · 여권사진 · 서명사진 등 KYC 원본 유출, memberLedger에 임의 금액 직접 삽입, partnerStaff 운영자 계정 탈취.

개선 방향
  1. firestore.rules + firestore.indexes.json을 저장소에 추가하고 firebase.json에 연결
  2. 기본 자세를 allow read, write: if false로 두고 필요한 경로만 여는 화이트리스트 방식
  3. 돈 컬렉션(memberLedger · ledger · mainCageLedger · shareLedger)은 클라이언트 쓰기 전면 거부
  4. accounts의 여권 · 서명 이미지는 Firestore가 아니라 Storage로 옮기고 서명 URL로만 접근
  5. CI 배포 경로에 규칙을 포함하고 @firebase/rules-unit-testing 기반 규칙 테스트 추가

P0 S2 APP_API_SECRET 공개 번들 하드코딩

index.html:6138

const TG_APP_API_SECRET = '19293b49…7702da0';   // 실제 값은 전체가 커밋되어 있음

docs/how-to-deploy.md:38은 정반대를 지시합니다 — "값을 따옴표와 함께 소스 코드나 Git에 저장하지 마세요." 브라우저 view-source로 즉시 획득 가능하므로 Cloud Functions 3종의 인증은 사실상 없는 것과 같습니다.

함수비밀값 유출 시 가능한 행위
getTelegramLinks계좌ID별 Telegram 사용자명 · chatId 열거 (PII 수집)
sendTelegramMessage실제 고객에게 임의 문구 발송. 앱이 쓰는 "출금 인증 요청" 형식을 그대로 흉내내면 완성형 피싱
deleteTelegramLink임의 계정의 연동 해제 (서비스 방해)

CORS는 방어가 아닙니다. functions/index.js:19-28의 applyCors는 Access-Control-Allow-Origin을 설정만 하고 req.get('origin')을 읽지 않습니다. CORS는 브라우저 정책이라 curl은 무시합니다. 따라서 docs/reference-cloud-functions.md:15의 "앱용 엔드포인트는 Origin, 메서드, X-App-Secret을 확인합니다"는 사실이 아닙니다.

개선 방향
  1. 비밀값 회전이 먼저. 이미 Git 히스토리에 남아 있으므로 코드에서 지우는 것만으로는 무효화되지 않음
  2. 공유 비밀값 모델 자체를 폐기. 브라우저에 두고 안전한 비밀값은 존재하지 않음 — Firebase Auth ID 토큰 검증(onCall 또는 verifyIdToken)으로 대체
  3. Origin을 실제로 검증하려면 req.get('origin')을 읽고 화이트리스트와 비교 (보조 수단이지 인증은 아님)

P1 S8 마스터 비밀번호 평문이 주석에 남음

index.html:6354-6357

// Master password hash — used for master login authentication (see attemptMasterLogin below).
// The password itself is unchanged ('kyle'); only its SHA-256 digest is stored/compared here,
// so the plaintext no longer sits in the page source for anyone skimming view-source.
const MASTER_RESET_PASSWORD_HASH = 'bb44bf07…6a3e896d';

해시로 바꾼 목적이 "평문이 페이지 소스에 남지 않게 한다"인데, 바로 그 평문이 두 줄 위 주석에 그대로 있습니다. 주석도 번들에 포함되어 view-source로 보이므로 조치 효과가 0입니다.

부수 문제: 솔트 없는 단일 SHA-256이라 이 정도 길이의 값은 레인보우 테이블로 즉시 역산됩니다. 주석을 지워도 해시 상수만으로 복원 가능합니다.

개선 방향
  1. 주석에서 평문 제거 + 비밀번호 자체를 변경 (이미 Git 히스토리에 남음)
  2. 클라이언트 상수 비교 방식을 폐기하고 마스터 인증을 서버 검증으로 이동
  3. 서버 이전 전까지의 임시 조치라면 최소한 솔트 + 반복 해시(PBKDF2)로 교체

케이지 단말은 시작할 때마다 전체 운영 이력을 통째로 내려받아 메모리에 보관합니다. 원장은 append-only이므로 운영 일수에 비례해 초기 로딩 시간과 읽기 과금이 선형 증가합니다. 시연 환경에서는 데이터가 적어 드러나지 않지만, 실제 운영 1개월 후부터 체감됩니다.

같은 코드 영역에 최근 개선(index.html:4168, 리스너 오류 후 자동 재구독)이 들어가 있어 안정성 쪽은 이미 손을 댄 상태입니다. 범위 제한만 추가하면 됩니다.

개선 방향
  1. 각 구독에 영업일 기준 범위 필터(where('dt','>=', 당일 개장시각)) 또는 limit 적용
  2. 과거 이력 조회는 별도의 명시적 조회 화면으로 분리 (구독이 아닌 단발 쿼리)
  3. firestore.indexes.json을 저장소에 편입 — 현재 복합 인덱스를 코드로 관리하지 않아 콘솔 수동 작업에 의존

모든 HTML · JS · CSS에 no-store가 걸려 있어 새로고침할 때마다 약 700 KB를 다시 받습니다(index.html 499 KB + shared/ 97 KB + 화면별 JS). 배포 즉시 반영을 노린 설정으로 보이지만, 모바일 회선에서 진행하는 시연이라면 초기 로딩이 눈에 띄게 느려집니다.

개선 방향
  1. HTML만 no-cache로 두고, JS/CSS는 파일명 또는 쿼리에 버전을 붙여 max-age를 길게 부여
  2. 빌드 단계를 도입하지 않겠다면 ?v=YYYYMMDD 수동 버전 파라미터만으로도 충분
  3. index.html의 CSS(501줄)와 JS(5,000줄 이상)를 별도 파일로 분리하면 캐시 효율이 크게 개선됨
