## 2. 높음

### DR-83: `account_status` 3값 중 2값이 도달 불가 — 그리고 현행 해지는 원장을 지운다

**등급: 높음** · 근거 [`001:69`](../../db/schema/001_types_and_extensions.sql#L69) · [`001:140`](../../db/schema/001_types_and_extensions.sql#L140) · [`05:202-203`](05-api-contract.md) · [`05:395`](05-api-contract.md) · `index.html:6210-6248`

#### 목표 측 — 선언은 셋, 경로는 하나

```sql
-- ddl/001:69
CREATE TYPE ledger.account_status AS ENUM ('active', 'suspended', 'closed');

-- ddl/001:140  감사 이벤트 종류
  'withdrawal', 'adjustment', 'period_settle', 'account_status'
```

**상태 변경이 감사 대상으로까지 선언돼 있다.** 그런데 상태를 바꿀 수단이 없다.

| 값 | 도달 경로 | 상태 |
|---|---|---|
| `'active'` | `op_open_account` ([05:395](05-api-contract.md)) | ✅ |
| `'suspended'` | 없음 | ❌ 6차 `DR-70` |
| `'closed'` | 없음 | ❌ **이 항목** |

`ddl/` 전수에서 계좌 상태를 바꾸는 op 함수는 0건이다 — `closed_by` 컬럼이 걸리는 곳은 게임(`010:518`·`:614`)과 기간(`011:316`·`:382`)뿐이고 계좌가 아니다. `05`의 계좌 엔드포인트는 넷이며(`POST /v1/accounts` 개설 · `PATCH /v1/accounts/{code}` **"KYC 수정 (자금 무관)"** · `GET` 2종), **해지도 정지도 없다.**

결과: `account_status` ENUM은 사실상 단일값이고, `'account_status'` 감사 이벤트는 **한 번도 발생할 수 없다.**

> **선언-only 패턴 세 번째 재발.** 4차 `DR-50`(역분개 타입은 있고 호출 경로 없음) → 6차 `DR-70`(`'suspended'` 값은 있고 조작 경로 없음) → 이번(`'closed'`). 이번 특이점은 **하나의 ENUM에서 두 값이 동시에 걸렸다**는 것이다. `DR-70`을 "차단 조작 경로 추가"로만 처리하면 `'closed'`는 그대로 남는다 — 둘을 한 항목으로 묶어야 한다.

#### 현행 측 — 해지가 원장을 물리 삭제한다

`_doWithdrawAccount(id)` (`index.html:6210`, 진입 `withdrawAccount()` `:6205`):

```js
// index.html:6231-6248
delete DB.accounts[id];
if(fbDb){
 const snap = await fbDb.collection('ledger').where('accountId','==',id).get();
 const batch = fbDb.batch();
 snap.forEach(d=>batch.delete(d.ref));      // ← 해당 계좌 원장 전량 삭제
 await batch.commit();
}
delete DB.pointsByAccount[id];
DB.pointsHistory = (DB.pointsHistory||[]).filter(h=>h.account!==id);
DB.eventHistory  = (DB.eventHistory ||[]).filter(h=>h.account!==id);
DB.hotels = (DB.hotels||[]).filter(b=>b.account!==id);
DB.cars   = (DB.cars  ||[]).filter(c=>c.account!==id);
DB.aero   = (DB.aero  ||[]).filter(a=>a.account!==id);
```

**두 가지가 동시에 일어난다.**

1. **append-only 원장에 대한 물리 삭제.** [01 §17](01-current-system.md) 10번("게임 취소가 문서 삭제")과 같은 부류이지만 대상이 자금 원장 그 자체다.
2. **상대 계정의 미러 행은 남는다.** [01 §4-1](01-current-system.md)이 "이미 복식부기다"라고 기록한 그 `MAIN-{branch}` 반대 분개가 짝 없이 남는다 — **해지 한 번마다 지점 하우스 잔액이 해당 계좌의 순입출금액만큼 틀어진다.** 잔액이 원장 전량 합산으로 파생되므로(01 §4) 이 오차는 즉시 화면에 반영되고, 되돌릴 근거 데이터는 이미 삭제됐다.

#### 이관 함의 — M11이 다루지 않는 구멍

[`07` M11](07-migration.md)은 "`accounts`가 `localStorage`에만 있어 Firestore 덤프만으로 복원 불가"를 다룬다. 해지된 계좌는 그보다 나쁘다 — **원장까지 없다.** Firestore 덤프에 흔적이 전혀 없으므로 **"애초에 없던 계좌"와 "해지된 계좌"를 구별할 방법이 없다.** 그리고 개시 잔액을 `MAIN-{branch}` 합산으로 산출한다면 그 값은 이미 오염돼 있다.

#### 필요 조치

- `ledger.op_set_account_status()` — `'suspended'`·`'closed'` 양쪽 (`DR-70`과 한 항목). 4-eyes 대상 여부 판정, `audit` 이벤트 `'account_status'` 발생
- `PATCH /v1/accounts/{code}/status` — `05` §3에 신규. 기존 `PATCH`의 "자금 무관" 범위와 분리
- **원장 삭제 금지를 명문화** — `04` 또는 `08-adr`에 "계좌 해지는 상태 전이이며 분개를 삭제하지 않는다"
- `07`에 **해지 계좌 이관 판정** — 현행에 이미 삭제된 원장은 복원 불가. 개시 잔액 산출 시 `MAIN-{branch}` 오염을 전제로 실사 대조 필요

검증 쿼리(구현 후): `SELECT count(*) FROM pg_proc WHERE proname LIKE 'op_%account_status%'` — 0이면 재발.

### DR-84: 롤링 커미션 요율의 권위가 UI select의 옵션 라벨이다

**등급: 높음** · 근거 `index.html:6770-6795` · `:703` · `:6916`·`:6923` · `:7127-7130`

#### 사슬

```
accounts.rate  "1.45%"                          계좌 등록 · 정보 수정에서 입력
  ↓  applyAccountRateToGameType()   :6770       바이인 화면에서 계좌 조회 시
#gType <option> "Rolling 1.45%"                 select 옵션 라벨로 주입 (프리셋에 없으면 동적 생성)
  ↓  :6916 · :6923                              바이인 확정
games.type  "Rolling 1.45%"                     게임 문서에 문자열로 복사
  ↓  loadSettleGame()  :7127-7130               정산 화면 로드
rate = Number(/([\d.]+)%/ 첫 매치)/100
comm = Math.round((g.rolling||0) * rate)        #settleRolling 프리필
  ↓  recalcSettle()  :7137-7139
result = Math.max(0, comm - fb)                 #settleResult 텍스트
  ↓  :7228
지급액                                           textContent를 되읽어 계좌 입금
```

**다섯 홉이고 그중 셋이 문자열이다.** 숫자가 **UI 위젯의 옵션 라벨을 통과한다.** [01 §6](01-current-system.md)의 `memo` 의미론 캐리어와 같은 부류인데, 이쪽은 계정 필드에서 시작해 DOM 텍스트에서 끝난다.

#### 프리셋 하나가 자릿수 단위로 틀린다

`#gType` 프리셋 3종 (`index.html:703`), 정규식은 **첫 퍼센트**를 잡는다:

| 프리셋 | 첫 매치 | 프리필 커미션 |
|---|---|---|
| `Rolling 1.5%` | `1.5` | 롤링 × 1.5% ✅ |
| `Rolling 1% + Share 10%` | `1` | 롤링 × 1% ✅ *(롤링이 앞이라 우연히 맞는다)* |
| **`Share 40%`** | **`40`** | **롤링 × 40%** ❌ |

셰어 딜의 배분율이 롤링 커미션 요율로 읽힌다. 운영자가 매번 덮어쓰는 것이 유일한 방어이며, 코드 주석(`:6767-6769`)은 덮어쓰기를 **정상 워크플로로 전제한다**: *"Staff can still override the selection manually afterward (e.g. for a Share-based deal)"*. 즉 이 프리셋은 "고치면 되는 버그"가 아니라 **설계가 사람의 개입을 요구하는 지점**이다.

#### 목표 측 — 요율의 소재를 정한 문서가 없다

- `04`: 롤링 커미션 정산 절 자체가 없다 (6차 `DR-66`, 차단)
- `ddl/005_games_rolling.sql`: 요율 컬럼도 커미션 모델도 없다
- `ledger.partner_profiles.share_rate_bp`는 **파트너 쉐어**용이며 케이지 손님 롤링 요율과 다른 축이다

> **8차 `DR-81`과 짝이다.** 저쪽은 플레이어 배당의 권위가 클라이언트 상수(`game-engine.js:14`)에만 있다는 것이고, 이쪽은 케이지 커미션 요율의 권위가 클라이언트 select 라벨에만 있다는 것이다. **금액을 정하는 숫자가 서버 어디에도 없다**는 같은 문장의 두 사례다.

#### 이관 함의

`games.type` 문자열이 **과거 게임에 적용된 요율의 유일한 기록**이다. 문자열 파싱으로만 복원할 수 있고, `Share 40%` 게임은 복원 자체가 모호하다 — 프리필 40%가 그대로 지급됐는지 운영자가 덮어썼는지는 `DB.settled.commission`과 `rolling`으로 **역산**해야 한다. 그리고 `DB.settled`는 `localStorage` 전용이다 (01 §7-0 · §17 12번).

#### 필요 조치

- `cage.games`에 `commission_rate_bp INT` — 바이인 시 계정 요율을 **스냅샷**한다. basis point 표기는 8차 `DR-77`의 규약을 따른다
- `games.type`은 표시용 라벨로 강등. 정산이 문자열을 파싱하지 않는다
- `04`의 롤링 커미션 절(`DR-66`)에 **요율 출처와 스냅샷 시점**을 명시
- 현행 코드에서 `Share 40%` 프리셋 처리 별도 수정 — 목표 설계와 무관하게 지금 오지급 프리필을 낸다

## 3. 중간

### DR-85: 정산 재실행 방지가 종료 게임에만 있다

**등급: 중간** · 근거 `index.html:7231` · `:7245-7248` · `:7249-7250` · `:7260-7263`

`_doSettleGame`은 `isEnded`(`:7231`)로 분기하며 **진행 중 게임도 정산 대상으로 명시 지원한다.**

| | 종료 게임 | 진행 중 게임 |
|---|---|---|
| 플래그 | `g.settled = true` (`:7246`) | **없음** |
| 드롭다운 | 재조회 시 제외 (`:7260-7263` 주석) | 계속 노출 |
| 레코드 | `DB.settled`에 push | `DB.settled`에 push |

`DB.settled`는 push-only이고 같은 `gameId`의 중복을 막는 검사를 `_doSettleGame` 안에서 찾지 못했다. 즉 **진행 중 게임은 몇 번이든 다시 정산할 수 있고, 매번 계좌에 입금된다.**

목표 측: `DR-66`이 요구하는 `cage.op_settle_commission()`에 멱등 제약이 없으면 그대로 이식된다. 6차 §2가 제안한 멱등키는 `settle:{game_no}:{seq}`인데 — **`seq`를 두는 순간 "몇 번까지 허용인가"가 정책 결정이 된다.** 진행 중 게임의 반복 정산이 업무상 정당한 행위인지(중간정산처럼) 아니면 사고인지를 먼저 정해야 키 형태가 결정된다.

> 8차 `DR-78`과 같은 계열이되 방향이 반대다. 저쪽은 **키가 하나뿐이라 충돌**해서 지급이 막히고, 이쪽은 **키가 없어서** 중복 지급이 뚫린다.

**필요 조치:** 반복 정산 허용 정책 결정 → 멱등키 형태 확정 → `04`에 명시 → `op_settle_commission` 제약. 현행 코드에도 진행 중 게임 재정산 가드가 별도로 필요하다.

### DR-86: 이벤트 커미션이 정산과 원자적이지 않고 실패가 남지 않는다

**등급: 중간** · 근거 `index.html:7259` · `:9028-9031` · `:9062-9075`

```js
// index.html:7259 — §7-0 말미. await 없음
payEventCommissionForSettle(g.account, g.rolling||0);
```

네 가지가 겹친다.

1. **`await` 없이 트리거된다.** 롤링 커미션 정산은 보너스 지급의 성공 여부를 모른 채 완료 토스트를 낸다.
2. **실패가 무기록이다.** `if(!txn) return` (`:9071`). 주석이 의도를 밝힌다 — 계좌에 닿지 못한 보너스를 "지급됨"으로 남기는 것보다 무음이 낫다는 판단이다. 판단 자체는 합리적이지만 **결과적으로 미지급이 어디에도 남지 않아 사후 보전이 불가능하다.**
3. **요율의 권위가 DOM이다.** `DB.eventRate`가 아니라 `document.getElementById('eventRate').value`를 읽는다 (`:9064`). 화면 값과 저장 값이 갈라지면 지급액은 화면을 따른다. `DR-84`와 같은 병이다.
4. **기간 판정이 문자열 비교다.** `nowStr >= DB.eventStart && nowStr <= DB.eventEnd` (`:9028-9031`), `'YYYY-MM-DDTHH:mm'` 형식. [01 §14](01-current-system.md)의 시각 처리 문제가 이벤트 활성 구간에서 재발한다 — 클라이언트 시계를 바꾸면 종료된 이벤트를 되살릴 수 있다.

목표 측: 6차 `DR-67`은 "이벤트 기간 엔티티(활성 구간·요율·활성화 감사)"까지만 요구하고 **연쇄 규약을 비워 뒀다.** 결정 필요:

| 안 | 의미 | 대가 |
|---|---|---|
| (a) 같은 트랜잭션 | 정산과 보너스가 함께 성공하거나 함께 실패 | 보너스 실패가 정산을 되돌린다 |
| (b) 아웃박스 비동기 + 실패 기록 | 정산은 확정, 보너스는 재시도 가능 | 아웃박스 인프라 필요 — `07`에 이미 있다 |
| (c) 별도 수동 연산 | 자동 연쇄 폐기 | 현행 UX 변경 |

**권장은 (b)다.** `07`이 텔레그램 통지용 아웃박스 경로를 이미 두었고(6차 §7 반증), 보너스 지급 실패는 정산 확정을 되돌릴 만한 사유가 아니다.

## 4. 등록하지 않은 4건

발견 8건 중 아래 넷은 **목표 설계의 요구사항을 바꾸지 않는다** — [`00` §7](00-system-map.md)의 기준이다.

| 발견 | 처리 | 근거 |

| `DB.blocks`만 계좌 해지 연쇄 삭제에서 제외된다 (`:6242-6248`) — 죽은 계좌의 차단 이력은 남고, 산 계좌의 해제 이력은 `splice`로 사라진다 | **`DR-70`에 흡수** | 차단 도메인의 생명주기 문제이며 별도 설계 요구를 만들지 않는다. `DR-70`의 "이력 테이블 + 재인증" 요구에 생명주기 규칙을 더하면 된다. [01 §3-4](01-current-system.md)에 기록 |
| `01` §9 교대 카운터 표에 게임 취소 음수 경로 4곳(`cancelGame()` `:6953`) 누락 | **해소 (2026-08-15)** | 6차 `DR-72` 사례. 이번 세션에 `applyShift` 호출 전수 재조사로 표에 추가했다 |

| 지급액 `result`를 `#settleResult`의 `textContent`에서 되읽는다 (`:7228`) | **`DR-84`에 흡수** | 같은 사슬의 마지막 홉이다 |

## 5. 이 회차가 남기는 것

### 5-1. 같은 문장에서 네 번 틀렸다

이 회차는 **자기 정정을 포함한다.** 경과를 그대로 기록한다.

| 시점 | `01` §3 `rate` 항목의 서술 | 판정 |
|---|---|---|
| 초판 (2026-08-10) | "커미션 계산 코드를 저장소에서 찾지 못했다. 미구현으로 보인다" | ❌ |
| 5차 | 위 문장을 근거로 **롤링 커미션 지급 자체가 없다**고 판정 (`DR-62`) | ❌ |
| 6차 | 지급 흐름은 있다고 정정. **다만 "수동 입력이며 `rate` 자동 계산은 없다"** | ❌ 절반 |
| 9차 1차 서술 (0단계 작업 중) | "이 필드를 읽는 코드를 찾지 못했다" — 6차 판정을 그대로 옮겨 적었다 | ❌ |
| 9차 최종 | **읽힌다.** `applyAccountRateToGameType()` (`:6770`)가 읽어 select 옵션에 주입한다 | ✅ |

**네 번 연속 틀렸고 이유는 매번 같다** — `rate`를 grep하면 정산 코드에 닿지 않는다. 값이 UI 위젯을 경유하기 때문이다.

### 5-2. 그래서 반복 실패 지점이 특정된다

6차 교훈은 *"서술이 없으면 대조 자체가 일어나지 않는다"*였다. 9차가 그 아래 층을 하나 더 판다 — **grep으로 추적되지 않는 데이터 흐름이 이 저장소의 구조적 사각지대다.**

같은 형태가 이미 세 번 나왔다:

| 사례 | 캐리어 | 등록 |
|---|---|---|
| 롤링 이벤트의 의미 구분 | `memo` 문자열 (`''` vs `'rolling'`) | [01 §6](01-current-system.md) |
| 케이지 커미션 요율 | `#gType` 옵션 라벨 → `games.type` 문자열 | `DR-84` |
| 플레이어 배당 | 클라이언트 상수 + 화면 표기(배수 vs 배당) | 8차 `DR-81` |

**대조 방법에 함의가 있다.** 남은 미검증 축을 볼 때 심볼 grep만으로는 부족하다 — 금액·요율·상태를 결정하는 값이 **어디서 와서 어디로 가는지** 홉 단위로 따라가야 한다.

## 7. 미검증 잔여

이번 회차가 해소하지 않은 대조 축:

- **`ddl/005`·`010`(케이지 게임 · 롤링 계층) vs `01` §7~§11 전량 대조** — 8차에서 이월. 이번 회차는 `005`에 요율 컬럼이 없다는 사실만 확인했다
