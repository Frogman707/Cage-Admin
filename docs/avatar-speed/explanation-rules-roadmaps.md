# 설명 — 게임 룰과 로드맵 알고리즘

> **분류**: Explanation (이해 지향)
> **작성 기준일**: 2026-08-15 · 브랜치 `backend`
> **관련 문서**: [엔진 레퍼런스](reference-game-engine.md) · [처리 흐름](explanation-round-flow.md) · [알려진 격차](explanation-known-gaps.md)

이 문서는 게임 규칙 자체를 다룹니다. 무엇을 구현했고, **실제 바카라와 어디가 다르며, 왜 그렇게
단순화했는지**를 설명합니다.

---

## 한 줄 요약

**규칙은 실제 바카라 그대로이고, 카드를 뽑는 방식만 다릅니다.** 서드카드 룰(푼토 반코 타블로),
배당, 페어, 타이 푸시, 로드맵 4종이 모두 표준을 따릅니다. 남은 차이는 덱 모델 하나 —
슈 대신 매번 52장에서 복원 추출합니다.

> **2026-08 변경**: 이 문서의 이전 판은 "서드카드 룰이 없는 2장 바카라"라고 설명했습니다.
> 그 서술은 더 이상 맞지 않습니다. 커밋 `9eec17d`("Deal to the punto banco tableau")에서
> `dealHand()`가 제거되고 `simulateRound()`가 전체 타블로를 구현했습니다. 같은 커밋이
> 파생 로드의 연속 규칙도 표준에 맞게 고쳤습니다.

## 덱 모델 — 무한 덱, 복원 추출

실제 바카라는 8덱(416장)을 슈에 넣고 소진될 때까지 뽑습니다. 이 구현은 다릅니다.

```js
function randCard(){
  const rank = CARD_RANKS[Math.floor(Math.random()*CARD_RANKS.length)];  // 13종에서 균등
  const suit = CARD_SUITS[Math.floor(Math.random()*CARD_SUITS.length)];  // 4종에서 균등
  return {rank, suit};
}
```

매번 52장 전체에서 독립적으로 뽑습니다. 서드카드도 같은 함수를 쓰므로 한 라운드에 최대 6장이
모두 복원 추출입니다. 결과적으로:

- **같은 카드가 한 라운드에 중복 등장할 수 있습니다.** `♠A ♠A` 핸드가 나옵니다.
- **카드 카운팅이 성립하지 않습니다.** 이전에 무엇이 나왔든 다음 확률은 변하지 않습니다.
- **슈가 소진되지 않습니다.** 테이블 문서의 `shoeNo`는 표시용 숫자일 뿐이고 자동으로 증가하지도
  않습니다. "슈 체인지 요청" 기능이 있지만 처리하는 코드가 없습니다
  ([G-10](explanation-known-gaps.md#g-10--avatarservicerequests에-소비자가-없다)).

각 랭크가 뽑힐 확률이 정확히 1/13이라는 점도 실제와 다릅니다. 다만 카드값 0에 해당하는 랭크가
10·J·Q·K 네 종으로 4/13을 차지하는 것은 실제 덱과 같으므로, **점수 분포 자체는 실제 덱과 거의
같습니다.** 달라지는 것은 복원 추출로 인한 독립성입니다.

`Math.random()`은 암호학적으로 안전하지 않고 공인 RNG 감사를 받지 않았습니다. 시연용입니다.

## 카드값과 점수

| 랭크 | 값 |
| --- | --- |
| A | 1 |
| 2 ~ 9 | 액면 그대로 |
| 10, J, Q, K | 0 |

점수는 **핸드에 든 모든 카드값** 합의 1의 자리입니다. 최소 0, 최대 9.

```js
function handTotal(cards){
  return cards.reduce((sum,c)=>sum+cardValue(c.rank), 0) % 10;
}
```

```
♠7 + ♥8      = 15 → 5
♦K + ♣9      =  9 → 9   (K는 0)
♠A + ♥A      =  2 → 2   (페어이기도 함)
♠4 + ♥A + ♦6 = 11 → 1   (서드카드 포함 3장)
```

장수 제한이 없으므로 서드카드가 들어온 3장 핸드에도 같은 함수를 씁니다.
여기까지는 실제 바카라와 완전히 동일합니다.

## 서드카드 룰 (푼토 반코 타블로)

실제 바카라의 가장 복잡한 부분이 그대로 구현되어 있습니다. 아무도 선택하지 않습니다 —
두 점수만으로 순서가 전부 결정되는 고정 표입니다.

### 1. 내추럴이면 양쪽 스탠드

```js
if (pt < 8 && bt < 8){ /* 드로우 판정 */ }
```

플레이어든 뱅커든 처음 두 장이 8 또는 9면 (내추럴) 즉시 종료입니다. 어느 쪽도 카드를 더
받지 않습니다.

### 2. 플레이어 먼저

| 플레이어 점수 | 동작 |
| --- | --- |
| 0 ~ 5 | 서드카드 1장 |
| 6 ~ 7 | 스탠드 |

### 3. 뱅커는 플레이어의 서드카드를 보고 결정

플레이어가 **받지 않았으면** 뱅커도 플레이어와 같은 규칙(0~5 드로우, 6~7 스탠드)을 씁니다.

플레이어가 **받았으면**, 뱅커 점수와 플레이어 서드카드값 `v`의 조합으로 결정합니다:

| 뱅커 점수 | 드로우 조건 |
| --- | --- |
| 0 ~ 2 | 무조건 드로우 |
| 3 | `v !== 8` |
| 4 | `v` ∈ 2~7 |
| 5 | `v` ∈ 4~7 |
| 6 | `v` ∈ {6, 7} |
| 7 | 스탠드 |

코드에서는 삼항 연산자 체인 하나로 표현됩니다:

```js
const bankerDraws =
  p3 === null ? bt <= 5 :
  bt <= 2     ? true :
  bt === 3    ? v !== 8 :
  bt === 4    ? v >= 2 && v <= 7 :
  bt === 5    ? v >= 4 && v <= 7 :
  bt === 6    ? v === 6 || v === 7 :
                false;
```

### 페어는 서드카드보다 먼저 확정된다

```js
const playerPair = player.cards[0].rank === player.cards[1].rank;   // 드로우 이전
```

3장 핸드에서 첫 두 장이 같은 랭크면 페어이고, 세 번째 카드가 같은 랭크로 들어와도 페어에는
영향이 없습니다. 실제 사이드벳 규칙과 같습니다.

### 이 구현이 정확히 맞춘 것

- **뱅커 우위가 실제로 생깁니다.** 뱅커는 플레이어의 서드카드를 본 뒤 결정하므로 정보 우위가
  있고, 그래서 승률이 플레이어보다 약간 높습니다. 뱅커 배당에 5% 커미션이 붙는 이유가
  비로소 성립합니다.
- **타이 비율이 정상 범위로 내려갑니다.** 서드카드가 점수를 흩어놓으므로 두 핸드가 같은 점수에
  걸릴 확률이 2장 비교 때보다 낮아집니다.
- **`rounds` 스키마가 가변 길이를 받습니다.** `playerCards`/`bankerCards`는 2개 또는 3개이며,
  두 배열의 길이가 서로 다를 수 있습니다.
- **딜링 애니메이션이 카드 수를 가정하지 않습니다.** `dealSequence(sim)`이 실제 뽑힌 카드에서
  순서를 만들어 냅니다.

### 아직 실제와 다른 것

덱 모델 때문에 **확률 분포가 실제 슈와 완전히 같지는 않습니다.** 복원 추출이라 각 랭크가
항상 1/13이고, 이미 나온 카드가 다음 확률에 영향을 주지 않습니다. 실제 8덱 슈에서는
소진에 따라 확률이 미세하게 움직입니다.

카드값 0인 랭크(10·J·Q·K)가 4/13을 차지하는 비율 자체는 실제 덱과 같으므로 점수 분포는
가깝지만, 하우스 엣지를 소수점까지 주장할 근거는 되지 않습니다. `Math.random()`이 공인 RNG
감사를 받지 않았다는 점도 그대로입니다.

## 페어 판정

```js
const playerPair = player.cards[0].rank === player.cards[1].rank;
```

**랭크만 비교하고 무늬는 무시합니다.** `♠7 ♥7`도 페어, `♠7 ♠7`도 페어입니다. 실제 바카라의
페어 사이드벳과 같은 규칙입니다 (무늬 무관). **처음 두 장만** 봅니다 — 서드카드는 페어 판정에
들어가지 않습니다.

복원 추출 때문에 완전히 동일한 카드(`♠7 ♠7`)가 나올 수 있는데, 실제 8덱 슈에도 같은 카드가
8장 있으므로 불가능한 조합은 아닙니다. 확률만 다릅니다.

페어는 P/B/T 결과와 **독립적으로** 정산됩니다. 플레이어가 페어이면서 뱅커가 이기는 라운드에서
플레이어 페어 베팅은 당첨입니다.

## 배당표

`PAYOUT` 상수는 **총 반환 배수(gross)**입니다 — 원금이 포함되어 있습니다.

| 베팅 | 코드 배수 | 순배당 | 승리 조건 | 타이일 때 |
| --- | --- | --- | --- | --- |
| 플레이어 | 2.0 | 1 : 1 | `result === 'player'` | **푸시** (원금 반환) |
| 뱅커 | 1.95 | 0.95 : 1 | `result === 'banker'` | **푸시** (원금 반환) |
| 타이 | 9.0 | 8 : 1 | `result === 'tie'` | 당첨 |
| 플레이어 페어 | 12.0 | 11 : 1 | `playerPair` | 결과와 무관 |
| 뱅커 페어 | 12.0 | 11 : 1 | `bankerPair` | 결과와 무관 |

배당액은 `Math.round(amount * mult)`로 계산합니다. 뱅커 배당에서 원 단위 반올림이 생길 수
있습니다 (`10001 × 1.95 = 19501.95` → `19502`).

### 타이 푸시가 원장에 남는 방식

P/B 베팅에 타이가 나오면 배수 `1`, 즉 건 금액이 그대로 돌아옵니다. 하지만 베팅 시점에 이미
`-N`이 원장에 기록되었으므로 정산에서 `+N`을 다시 씁니다.

```
memberLedger:
  { category: 'bet',    amount: -50000, betType: 'banker', relatedRoundId: 'a1b2...' }
  { category: 'payout', amount: +50000,                    relatedRoundId: 'a1b2...' }
```

두 줄을 남기는 편이 순증감 0을 아무것도 기록하지 않는 것보다 낫습니다. "이 라운드에 베팅했고
환불받았다"는 사실이 원장 자체로 증명되기 때문입니다.

패배한 베팅은 반대로 `bet` 한 줄만 남습니다. `payout === 0`이면 `settleBet`이 문서를 쓰지
않습니다.

### 실제 카지노와 다른 점

**커미션 처리 방식이 다릅니다.** 실제 바카라는 보통 뱅커 승리 시 1:1로 지급한 뒤 5% 커미션을
별도로 징수합니다(또는 노커미션 바카라에서는 뱅커 6점 승리를 0.5:1로 지급). 여기서는 배당 배수에
커미션을 미리 녹여 `1.95`로 처리합니다. 회원 입장의 순수령액은 같지만 **커미션이 원장에 별도
항목으로 남지 않아 정산 리포트에서 커미션 총액을 뽑을 수 없습니다.**

**한도가 강제되지 않습니다.** 테이블 문서에 `betMin`/`betMax`가 있고 회원 문서에도 있지만
`placeBet`도 `placeSpeedBet`도 이를 검사하지 않습니다. 화면에 한도가 표시될 뿐입니다 —
[G-02](explanation-known-gaps.md#g-02--베팅-한도가-어디에서도-강제되지-않는다).

## 로드맵 (로드) — 왜 4종인가

바카라 테이블 옆 모니터에 붙어 있는 그 보드입니다. 실제 카지노는 보통 비드 플레이트 + 빅로드 +
파생 3종을 표시하고, 이 구현도 같은 구성을 그립니다.

로드맵의 목적은 **패턴을 시각화하는 것**이지 확률을 바꾸는 것이 아닙니다. 각 라운드는 독립
시행이므로 로드가 보여주는 "흐름"에 예측력은 없습니다. 그래도 플레이어가 이것을 보고 베팅하므로
실제 서비스와 같은 규칙으로 그려야 시연이 설득력을 갖습니다.

```
┌─────────────────────────┬──────────────────────────────────┐
│  P/B/T 승수 + 페어 횟수   │  빅로드 (대로)          6행        │
│                         ├──────────────────────────────────┤
│  비드 플레이트 (육매)     │  대안목 (빅아이)        3행        │
│  값 바뀌면 새 열, 6행     ├──────────────────────────────────┤
│  P/B/T 각각 자기 열       │  소로 (스몰로드)        3행        │
│  최근 40개               ├──────────────────────────────────┤
│                         │  갑충로 (카카로치)      3행        │
└─────────────────────────┴──────────────────────────────────┘
                                    우측 가장자리에 P/B 범례 레일
```

`avatarScoreboardHtml(idSuffix)` 하나가 이 배치를 만들며, 아바타 테이블과 스피드 상세 화면이
같은 함수를 씁니다.

## 비드 플레이트 (진주로, 육매, Bead Plate)

> **2026-08 변경**: 이 로드의 규칙이 바뀌었습니다. 예전에는 "6개씩 무조건 세로로 채우는 엄격한
> 시간순"이었지만 (한 열에 P/B/T가 섞임), 지금은 **빅로드와 같은 열 규칙**을 씁니다.
> 이 프로젝트가 참고한 실물 보드가 그렇게 그리기 때문입니다 (커밋 `6a82b3d`).

```js
results.forEach((r,i)=>{
  if (cols.length && cols[cols.length-1].value===r) cols[cols.length-1].items.push(pf);
  else cols.push({value:r, items:[pf]});     // 값이 바뀌면 새 열
});
```

```
결과: P B B T T T P P

1열  2열  3열  4열
 P    B    T    P
      B    T    P
           T
```

- **연속된 같은 값이 세로로 쌓이고, 값이 바뀌면 새 열**이 시작됩니다.
- 따라서 **한 열에는 P/B/T 중 한 종류만** 들어갑니다.
- 타이도 자기 열을 가집니다. 빅로드처럼 직전 열에 흡수되지 않습니다 — 그것이 지금
  비드 플레이트와 빅로드의 결정적 차이입니다.
- 한 열이 6개(`BEAD_ROWS`)를 넘으면 다음 열로 이어 그립니다 (빅로드와 같은 드래곤 테일).
- 각 비드에 결과 글자(`P`/`B`/`T`)와 페어 코너 점이 함께 찍힙니다.

### 왜 최근 40개만 그리는가

빅로드는 최근 90개, 비드 플레이트는 최근 40개(`BEAD_WINDOW`)를 그립니다
([`avatar/app.js:572`](../../avatar/app.js#L572)).

열 그룹핑을 쓰면 결과가 자주 바뀔수록 열 수가 늘어 슈 전체가 패널보다 훨씬 넓어집니다.
극단적으로 P/B가 매 라운드 교대하면 결과 하나당 열 하나가 되므로, 250라운드는 250열입니다.

예전에 전체를 그렸던 이유(6개씩 순서대로 채우는 구조에서는 앞을 자를 때마다 격자가 통째로
재배치됨)는 지금 규칙에서는 성립하지 않습니다. 열 단위로 쌓이므로 앞을 잘라도 뒤쪽 배치가
흔들리지 않습니다 — 빅로드와 같은 이유로 슬라이스가 안전해졌습니다.

## 빅로드 (대로, Big Road)

가장 중요한 로드입니다. 나머지 3종이 전부 이것에서 파생됩니다.

### 규칙 세 가지

**1. 같은 편이 이기면 세로로 쌓는다. 편이 바뀌면 새 열을 시작한다.**

```js
if (cols.length && cols[cols.length-1].side === r){
  cols[cols.length-1].items.push(r);      // 같은 편 → 아래로
} else {
  cols.push({side:r, items:[r], pairs:[pf], ties:0});   // 편 교체 → 새 열
}
```

```
결과: B B B P P B P P P P

  1열  2열  3열  4열
   B    P    B    P
   B    P         P
   B              P
                  P
```

**2. 타이는 새 열을 만들지 않는다. 직전 열의 카운터를 올린다.**

```js
if (r === 'tie'){
  if (cols.length) cols[cols.length-1].ties = (cols[cols.length-1].ties||0) + 1;
  else cols.push({side:null, items:[], pairs:[], ties:1});
  return;
}
```

타이는 승부가 나지 않은 라운드이므로 진행 방향을 바꾸지 않습니다. 실제 보드에서도 초록색
사선(슬래시)으로 표시하고 흐름은 그대로 둡니다.

**3. 열이 6행을 넘으면 옆으로 이어 그린다 (드래곤 테일).**

```js
for (let start = 0; start < col.items.length; start += maxRows){
  // maxRows개씩 잘라 각각 별도 .br-col로 렌더
}
```

9연속 뱅커가 나오면:

```
  1열  2열
   B    B      ← 7번째부터 옆 열로 이어짐
   B    B
   B    B
   B
   B
   B
```

잘라내거나 "+3" 같은 카운터로 요약하지 않습니다. 실제 보드가 그리는 방식 그대로입니다.

### 단순화된 부분 — 타이 배지 위치

실제 보드는 타이가 발생한 **그 셀**에 슬래시를 긋습니다. 이 구현은 열의 **첫 번째 셀**에만
누적 카운트를 표시합니다.

```js
const showTie = idx === 0 && col.ties > 0;
```

`ties`가 열 단위 카운터일 뿐 어느 셀 뒤에 타이가 있었는지 기록하지 않기 때문입니다. 실제와
비교하면 "이 열에서 타이가 2번 있었다"는 정보는 남지만 "3번째 뱅커 뒤였다"는 정보는 사라집니다.

셀 단위로 정확히 그리려면 `Column`에 셀별 타이 배열이 필요합니다. 시각적 인상이 거의 같아
비용 대비 효과가 낮다고 판단한 것으로 보입니다.

### 선행 타이 열

슈의 **첫 결과가 타이**면 열이 하나도 없는 상태이므로 `{side: null, items: [], ties: 1}` 열이
만들어집니다. 렌더링에서는 초록 점 하나로 표시됩니다.

```js
if (!col.side){ cells.push(`<div class="br-col"><div class="br-cell tie-only">${col.ties}</div></div>`); }
```

이 열이 파생 로드 계산에서 문제를 일으킵니다 (아래 참고).

## 파생 로드 3종 — 대안목 / 소로 / 갑충로

빅로드가 "무슨 일이 일어났나"를 보여준다면, 파생 로드는 **"그 일이 얼마나 규칙적인가"**를
보여줍니다.

세 로드는 **완전히 같은 알고리즘**을 쓰고 **비교하는 거리만 다릅니다.**

| 로드 | 한국어 | `offset` | 의미 |
| --- | --- | --- | --- |
| Big Eye Boy | 대안목 | 1 | 바로 앞 열과 비교 |
| Small Road | 소로 | 2 | 두 열 앞과 비교 |
| Cockroach Road | 갑충로 | 3 | 세 열 앞과 비교 |

### 알고리즘

빅로드의 각 셀마다 마크를 하나씩 만듭니다.

```js
if (j === 0){
  // 열의 첫 셀 = 진행 방향이 바뀐 순간
  // offset칸 뒤의 두 열 길이가 같은가?
  mark = cols[i-offset].items.length === cols[i-offset-1].items.length ? 'red' : 'blue';
} else {
  // 열이 이어지는 중
  // offset칸 뒤 열의 행 j와 행 j-1, 두 칸을 비교
  mark = cols[i-offset].items.length === j ? 'blue' : 'red';
}
```

의미로 풀면:

- **red = 반복 (패턴이 유지됨)**
- **blue = 이탈 (패턴이 깨짐)**

**열의 첫 셀**은 "방금 편이 바뀌었는데, 과거 같은 위치에서도 열 길이가 균일했는가"를 묻습니다.
균일했으면 red.

**이어지는 셀**은 "과거 대응 열의 이 행과 바로 윗행, 두 칸이 같은 상태인가"를 묻습니다.
둘 다 차 있거나 둘 다 비어 있으면 red(패턴 반복), 정확히 하나만 차 있으면 blue(패턴 깨짐)입니다.

대상 열 길이를 `L`이라 하면:

| `L` | 행 `j-1` | 행 `j` | 마크 |
| --- | --- | --- | --- |
| `L > j` | 차 있음 | 차 있음 | red |
| `L === j` | 차 있음 | 비어 있음 | **blue** (열이 여기서 끝남) |
| `L < j` | 비어 있음 | 비어 있음 | red |

> **2026-08 수정** (커밋 `9eec17d`): 예전 식은 `L > j ? red : blue`였습니다. `L < j`인 경우
> (두 칸 모두 비어 있음)까지 blue로 찍어 표준 규칙과 어긋났습니다. 현재 식
> `L === j ? blue : red`는 표준과 정확히 일치합니다.

### 시작 시점

```js
for (let i = offset; i < cols.length; i++){
  ...
  if (j === 0 && i < offset + 1) continue;
}
```

- `j > 0` 셀은 `i = offset` 열부터 나옵니다.
- `j = 0` 셀은 `i = offset + 1` 열부터 나옵니다.

대안목(`offset = 1`)이면 **빅로드 2열의 2번째 셀** 또는 **3열의 1번째 셀**부터 시작합니다.
표준 규칙과 정확히 일치합니다.

### 마크를 다시 열로 묶는다

파생 로드도 빅로드처럼 열 구조를 가집니다. `groupIntoRoadColumns()`가 연속된 같은 색을 한 열로
묶고, `renderRoadColumns()`가 3행씩 잘라 그립니다.

```js
function renderDerivedRoad(marks, style){
  const cols = groupIntoRoadColumns(marks);
  return renderRoadColumns(cols, m=>`<div class="dr-cell ${m}${style?' '+style:''}"></div>`, 3);
}
```

3행인 이유는 빅로드 아래 한 패널에 세 로드를 쌓아야 하기 때문입니다. 빅로드의 6행을 그대로
쓰면 세로 공간이 부족합니다.

### 세 로드는 모양으로 구분한다

| 로드 | CSS | 모양 |
| --- | --- | --- |
| 대안목 | (기본) | 빈 링 ○ |
| 소로 | `.filled` | 채워진 점 ● |
| 갑충로 | `.diagonal` | 대각선 ╱ |

색(red/blue)은 세 로드 공통이고, 모양이 어느 로드인지를 말합니다. 화면 우측의 P/B 범례 레일이
같은 3종 기호를 설명합니다.

### 알려진 엣지 케이스

슈의 첫 결과가 타이면 `cols[0]`이 `{side: null, items: []}`가 됩니다. `deriveRoad`는
`if (!col.side) continue`로 **자기 자신이 타이 열일 때는 건너뛰지만**, `cols[i-offset]`이
타이 열인 경우는 걸러내지 않습니다. 길이 0인 열과 비교하게 되어 마크가 왜곡됩니다.

발생 조건이 좁고(슈 첫 라운드가 타이) 파생 로드가 장식적 지표라 실무 영향은 작지만, 정확히는
버그입니다.

## 테이블 통계

로비 카드와 스피드 타일 하단에 붙는 숫자들입니다.

### P/B/T 승수 — `tableWinCounts`

단순 카운트입니다. 항상 세 키가 존재하고 초기값 0입니다.

### 연속 승수 — `trailingStreak`

```js
const nonTie = results.filter(r => r !== 'tie');   // 타이 제거
const last = nonTie[nonTie.length-1];
let len = 0;
for (let i = nonTie.length-1; i >= 0; i--){ if (nonTie[i] === last) len++; else break; }
```

**타이는 연속을 끊지도, 늘리지도 않습니다.** 빅로드가 타이에 새 열을 만들지 않는 것과 같은
원칙입니다.

```
['player','banker','tie','banker']  →  {side:'banker', len:2}
```

`len >= 3`이면 🔥 배지가 붙고, 로비 정렬 옵션 "좋은 흐름순"의 정렬 키가 됩니다.

"좋은 흐름"은 물론 통계적 의미가 없습니다. 연속이 길다고 다음 결과가 예측되지 않습니다. 플레이어
심리에 맞춘 UI 장치입니다.

### 베팅 총액 — `tableBetVolume`

`total`은 전체 합, `today`는 `createdAt` 앞 10자가 오늘 날짜인 것들의 합입니다.

이 함수는 `createdAt`이 **문자열일 때만** 동작합니다. 실제 게임 플레이가 만든 원장 문서는
`Timestamp` 객체를 가지므로 `TypeError`가 납니다 —
[G-06](explanation-known-gaps.md#g-06--tablebetvolume이-timestamp-createdat에서-typeerror를-던진다).

## 실제 바카라와의 차이 정리

| 항목 | 실제 바카라 | 이 구현 | 영향 |
| --- | --- | --- | --- |
| 덱 | 8덱 슈, 비복원 | 무한 덱, 복원 | **유일하게 남은 규칙 차이.** 카운팅 불가, 중복 카드 가능 |
| 서드카드 룰 | Tableau 적용 | **동일** (전체 타블로 구현) | — |
| 뱅커 우위 | 서드카드 룰에서 발생 | **동일** (뱅커가 플레이어 서드카드를 보고 결정) | 뱅커 커미션의 근거가 성립 |
| 내추럴 8·9 | 양쪽 스탠드 | 동일 | — |
| 카드값 | A=1, 10JQK=0 | 동일 | — |
| 페어 판정 | 처음 두 장의 랭크 일치 | 동일 | — |
| 타이 푸시 | P/B 원금 반환 | 동일 | — |
| 커미션 | 별도 징수 | 배당 배수에 내재 (1.95) | 커미션 총액 집계 불가 |
| 베팅 한도 | 강제 | **미강제** | 한도 초과 베팅 가능 |
| 빅로드 | 표준 | 타이 배지 위치만 단순화 | 시각적 차이 미미 |
| 비드 플레이트 | 표준 (값 바뀌면 새 열) | 동일 | — |
| 파생 로드 3종 | 표준 | 표준 (선행 타이 열 엣지 케이스만 결함) | 거의 동일 |
| 슈 관리 | 슈 소진 시 교체 | `shoeNo`는 표시용, 교체 없음 | 슈 체인지 요청이 처리되지 않음 |
| RNG | 공인 감사 | `Math.random()` | 결과 신뢰 불가 |

**규칙과 로드맵은 실제와 사실상 같습니다.** 남은 차이는 덱 모델과 RNG 두 가지입니다.
시연에서 보드와 딜링을 보여주는 것은 설득력이 있지만, **확률이나 하우스 엣지를 수치로 주장하면
안 됩니다** — 복원 추출이라 실제 슈의 분포와 미세하게 다르고, `Math.random()`은 감사 대상이
아닙니다.
